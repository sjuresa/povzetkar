# Retrospective: v0.11.0 (API-First & Advanced Security)

**Status:** Draft
**Date:** [TBD]

## Preliminary Notes from Planning
*   **Focus:** Decoupling the frontend via REST API and implementing fine-grained Permission-Based Access Control (PBAC).
*   **Process Integrations:** Included "Test Data Builder" pattern from v0.10 learnings and "Automated Dependency Vulnerability Scanning" from methodology proposals.
*   **Architecture Goal:** Prevent a backend-driven API design by explicitly spiking the frontend specification first.

## 1. What Went Well
*   The explicit separation of the Frontend Specification (Task 1) and API Contract (Task 2) successfully prevented a backend-driven API design, allowing for the creation of a clean BFF (Backend-For-Frontend) structure.
*   Rigorous PR review of the API contract caught numerous REST inconsistencies early (e.g., correct `PATCH` vs `PUT` semantics, 0-indexed pagination, enum definitions), significantly reducing future technical debt.
*   Implemented the Test Data Builder pattern across the test suite, significantly reducing boilerplate and resolving brittleness associated with core entity creation in tests.
*   The hybrid PBAC implementation successfully met the requirement of granular permissions without requiring immediate, complex database migrations, keeping the development velocity high.
*   The implementation of async background jobs through a persistent `BackgroundJob` entity provides much-needed visibility and auditability into system operations, addressing a key visibility gap in previous versions.
*   The rigorous PR review process successfully caught missing edge-case tests (e.g., `ContentSource` deletion) and security vulnerabilities (e.g., exposing stack traces in Background jobs), proving the value of the review cycle in hardening the API.

## 2. What Didn't Go Well
*   Asynchronous execution in integration tests proved tricky. Initial tests failed because they asserted final states before the async operation had finished. Moving to a more robust "wait-and-verify" or asserting initial "QUEUED" state was necessary.
*   Transaction management in background jobs (using `execute()` with `@Transactional` services) requires careful handling of context and ensures entities are correctly reloaded or attached.

## 3. What Have We Learned
*   True asynchronous execution via `Infrastructure.getDefaultExecutor()` is superior to simpler `@Asynchronous` patterns for control, but requires explicit transaction handling within the executor block.
*   Parallelizing classic ORM backend queries within a `Uni` context requires wrapping the blocking IO calls in explicit scoped transactions (`QuarkusTransaction.requiringNew().call(...)`) to avoid decoupled thread failures.
*   Stable `equals` and `hashCode` implementation (using business keys or persistent IDs) is critical for entities used in async collections or cache.
*   Paginated endpoints returning entities with relationships are highly susceptible to N+1 query performance degradation. Implementing a two-step query pattern (fetch IDs, then fetch full entities via `JOIN FETCH`) is a necessary practice for avoiding memory bottlenecks.
*   Security evaluation must be granular down to the DTO field level when endpoints aggregate data requiring different permission sets (e.g. `TOPIC_VIEW` vs `BRIEFING_VIEW`).
*   Timezone handling in date-bound integration tests must be explicitly set to UTC (`java.time.ZoneOffset.UTC`) to prevent CI flakiness.
*   Quarkus `@RolesAllowed` evaluates array values using logical OR semantics, natively handling scenarios where an endpoint serves partial data depending on the presence of individual roles within that array.
*   In a reactive Mutiny pipeline, separating blocking I/O (database queries) from data transformations (DTO mapping) into distinct stages improves code clarity and ensures that worker threads are only utilized for the necessary blocking operations.
*   Returning a `Uni` from a JAX-RS method makes the *response* asynchronous, but the method body still begins execution on the caller thread (event loop). If the initial logic (e.g., getting the authenticated user) is blocking, you must either use the `@Blocking` annotation or explicitly offload the blocking call to a worker pool to prevent `BlockingOperationNotAllowedException`.

## 4. Action Items for Next Version
*   Standardize the `BackgroundJob` pattern for other long-running tasks like OCR or embedding generation.
