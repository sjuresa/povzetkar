# Retrospective: v0.11.0 (API-First & Advanced Security)

**Status:** Draft
**Date:** [TBD]

## Preliminary Notes from Planning
*   **Focus:** Decoupling the frontend via REST API and implementing fine-grained Permission-Based Access Control (PBAC).
*   **Process Integrations:** Included "Test Data Builder" pattern from v0.10 learnings and "Automated Dependency Vulnerability Scanning" from methodology proposals.
*   **Architecture Goal:** Prevent a backend-driven API design by explicitly spiking the frontend specification first.

## 1. What Went Well
*   The explicit separation of the Frontend Specification (Task 1) and API Contract (Task 2) successfully prevented a backend-driven API design, allowing for the creation of a clean BFF (Backend-For-Frontend) structure.
*   Rigorous PR review of the API contract caught numerous REST inconsistencies early (e.g., correct `PATCH` vs `PUT` semantics, 0-indexed pagination, enum definitions), significantly reducing future technical debt.
*   Implemented the Test Data Builder pattern across the test suite, significantly reducing boilerplate and resolving brittleness associated with core entity creation in tests.
*   The hybrid PBAC implementation successfully met the requirement of granular permissions without requiring immediate, complex database migrations, keeping the development velocity high.
*   The implementation of async background jobs through a persistent `BackgroundJob` entity provides much-needed visibility and auditability into system operations, addressing a key visibility gap in previous versions.
*   The rigorous PR review process successfully caught missing edge-case tests (e.g., `ContentSource` deletion) and security vulnerabilities (e.g., exposing stack traces in Background jobs), proving the value of the review cycle in hardening the API.
*   Successfully implemented global response envelopes via a JAX-RS filter, which removed significant boilerplate from the resource classes and ensured perfect consistency in the JSON API structure.
*   Integrated Optimistic Locking across the entire API foundations. This required significant refactoring of all integration tests to support the `If-Match` header protocol, but it provides robust protection against concurrent data corruption.
*   Centralizing exception handling with JAX-RS `ExceptionMapper`s successfully standardized the error API response format while removing boilerplate from individual resource classes.

## 2. What Didn't Go Well
*   Asynchronous execution in integration tests proved tricky. Initial tests failed because they asserted final states before the async operation had finished. Moving to a more robust "wait-and-verify" or asserting initial "QUEUED" state was necessary.
*   Transaction management in background jobs (using `execute()` with `@Transactional` services) requires careful handling of context and ensures entities are correctly reloaded or attached.

## 3. What Have We Learned
*   True asynchronous execution via `Infrastructure.getDefaultExecutor()` is superior to simpler `@Asynchronous` patterns for control, but requires explicit transaction handling within the executor block.
*   Parallelizing classic ORM backend queries within a `Uni` context requires wrapping the blocking IO calls in explicit scoped transactions (`QuarkusTransaction.requiringNew().call(...)`) to avoid decoupled thread failures.
*   Stable `equals` and `hashCode` implementation (using business keys or persistent IDs) is critical for entities used in async collections or cache.
*   Paginated endpoints returning entities with relationships are highly susceptible to N+1 query performance degradation. Implementing a two-step query pattern (fetch IDs, then fetch full entities via `JOIN FETCH`) is a necessary practice for avoiding memory bottlenecks.
*   Security evaluation must be granular down to the DTO field level when endpoints aggregate data requiring different permission sets (e.g. `TOPIC_VIEW` vs `BRIEFING_VIEW`).
*   Timezone handling in date-bound integration tests must be explicitly set to UTC (`java.time.ZoneOffset.UTC`) to prevent CI flakiness.
*   Quarkus `@RolesAllowed` evaluates array values using logical OR semantics, natively handling scenarios where an endpoint serves partial data depending on the presence of individual roles within that array.
*   In a reactive Mutiny pipeline, separating blocking I/O (database queries) from data transformations (DTO mapping) into distinct stages improves code clarity and ensures that worker threads are only utilized for the necessary blocking operations.
*   Returning a `Uni` from a JAX-RS method makes the *response* asynchronous, but the method body still begins execution on the caller thread (event loop). If the initial logic (e.g., getting the authenticated user) is blocking, you must either use the `@Blocking` annotation or explicitly offload the blocking call to a worker pool to prevent `BlockingOperationNotAllowedException`.
*   When aggregating results from parallel queries in a Mutiny pipeline, using the **type-safe `with()` orchestration pattern** ensures compile-time type safety. However, always use **`Collections.emptyList()`** instead of `List.of()` as a default value for collections in these pipelines; `List.of()` (without arguments) can lead to improperly inferred `List<Object>` types that trigger `ClassCastException` during aggregation due to Java's type erasure.
*   Inlining specialized orchestration logic (like permission-guarded queries) into the main BFF `fetch` method is often superior to delegating to private helpers when those helpers only exist to wrap a single query with a permission check. This co-location improves code locality, makes the security model easier to audit, and slightly reduces pipeline complexity.
*   Configuring SpotBugs for iterative adoption requires correctly setting the threshold (`<threshold>High</threshold>`) in the Maven `pom.xml` to avoid blocking CI on pre-existing, lower-severity codebase warnings.
*   Integrating Trivy via GitHub Actions (`aquasecurity/trivy-action`) provides an excellent, frictionless mechanism for tracking dependency vulnerabilities without requiring local developer setup.
*   **API Envelopes & Filter Precision:** Centralizing API envelope wrapping is effective, but filters must be precise (e.g., targeting only successful 2xx responses). Wrapping error responses leads to unpredictable client-side behavior and complicates exception handling logic.
*   **Optimistic Locking Protocol:** Enforcing the `If-Match` header in integration tests highlighted the need for a consistent way to manage entity versions during test data setup. Ensuring that pre-assertions (like `428 Precondition Required`) are tested before successful mutations provides higher confidence in the concurrency protection logic.
*   **Security for Internal API Resources:** Resources utilized primarily by internal administrative UIs must still receive explicit `@RolesAllowed` annotations to prevent unauthorized access via the public API endpoints, as URL-based UI/API boundaries are insufficient for robust security.
*   **Exception Mapping over Manual Responses:** Utilizing the JAX-RS `ExceptionMapper` infrastructure is superior to manual error response construction. It provides a centralized point for sanitizing error messages (preventing sensitive info disclosure) and ensures a consistent RFC 7807 error structure within the global envelope.
*   **Systemic Pagination & Sorting:** Extracted repetitive query string manipulation into utility classes (`FilterBuilder`, `QueryParser`), ensuring consistent API behavior across list endpoints while resolving potential HQL injection vulnerabilities during dynamic parameter binding.
*   **Idempotency & Name Binding:** Implementing idempotency caching revealed that relying on general path-based endpoint filters can lead to unintended double-enveloping if the payload is dynamically serialized (like parsing to `JsonNode`). Relying on explicit `@NameBinding` (e.g. `@Idempotent`) mitigates brittle URL scanning, and ensuring global filters skip internal framework types maintains response consistency.
*   **MDC Propagation to Background Threads:** Quarkus propagates MDC values automatically across the reactive Vert.x event loop, but NOT through `Infrastructure.getDefaultExecutor()` worker threads. The correct pattern is to capture `MDC.get(key)` on the request thread before calling `execute(...)`, then restore it at the start of the lambda and clear it in a `finally` block.
*   **Audit Logging via ContainerResponseFilter:** Persisting audit records in a global `ContainerResponseFilter` is an effective cross-cutting strategy because the response HTTP status is only known at that point. The filter must use `QuarkusTransaction.requiringNew()` to isolate the audit write from any business transaction, and must swallow its own failures (logging them) to ensure audit persistence failures never surface as API errors to clients.


## 4. Action Items for Next Version
*   Standardize the `BackgroundJob` pattern for other long-running tasks like OCR or embedding generation.
*   Transition from path-prefix scanning to JAX-RS Name Binding for all security and enveloping filters to eliminate brittle URL dependency.
