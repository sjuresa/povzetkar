# Retrospective for Version 0.9.0

**Status:** Final
**Date:** 2026-02-05

## Preliminary Notes from Planning

*   **Focus:** This version focuses on "Operational Refinement & Admin Tools" — specifically improving visibility (GenAI usage, orchestration preview) and resilience (circuit breakers) before introducing multi-user complexity.
*   **Process:** We are formalizing our development methodology into a definitive guide (`docs/process/methodology.md`) to move beyond comparison documents.
*   **Testing Strategy:** We explicitly decided to avoid the `BaseUITest` pattern (which failed in v0.6.2) and instead rely on standard `@QuarkusTest` with explicit transaction management or `@TestTransaction`.
*   **Design Decision (Timezones):** We established a clear boundary for timezone handling: Server and Logs remain in UTC (via JVM flags), while the UI performs localization based on configuration (`povzetkar.ui.timezone`).
*   **Scope Refinement:** We refined the "Dry-run" concept into a "Fetch & Count" Preview mode. This avoids the complexity of a transactional rollback simulation while providing the necessary visibility to the admin.

## What Went Well?
*   **Methodology Consolidation:** Creating the definitive methodology document (POV-93) forced us to review all past retrospectives, effectively "baking in" the lessons learned (like TDD mandates and Spike usage) into the core process documentation.
*   **Persistent GenAI Usage Tracking (POV-95):** Successfully implemented persistent tracking of GenAI API key usage, addressing initial design flaws and ensuring data integrity across restarts. This involved creating a new Panache entity, a dedicated service, and updating existing components, all verified with comprehensive tests and a database migration.
*   **Clean UI Feature Implementation (POV-96):** The pagination feature for the admin history was implemented cleanly. The backend logic was well-encapsulated in the `AdminResource`, and the frontend changes in the Qute template were straightforward, improving UI usability without any breaking changes.
*   **Iterative Bug Fixing (POV-97):** Despite initial implementation flaws, the agent was able to iteratively diagnose and fix a series of complex, interconnected issues (AJAX vs. form submission, reactive blocking calls, session management in async contexts) to successfully deliver the preview and status management features.
*   **MCP for Dependency Research (POV-98):** The Context7 MCP server was effective for quickly researching the latest version of the `google-genai` dependency and confirming that response headers were accessible for future quota monitoring work.

## What Didn't Go Well?
*   **Process Adherence:** There were instances where the "Mandatory Workflow for Code Changes" was not strictly followed, specifically regarding the explicit approval step and plan archiving. This highlights the need for stricter internal enforcement of the sequential workflow.
*   **UI Implementation Gaps:** Initial implementations for new UI features (Preview, Status Management) failed to account for existing AJAX patterns in `admin.js`, leading to regressions and rework. This indicates a need to analyze client-side code before modifying server-side UI handlers.
*   **Reactive Programming Pitfalls:** Blocking calls were inadvertently introduced into reactive contexts, causing runtime exceptions. This reinforces the need for rigorous checks against blocking operations in `Uni`/`Multi` pipelines.
*   **Impact Analysis Gaps:** Modifications to shared utilities (`ViewUtils`, `GenAiPool`) caused cascading breakages in other components and tests. This underscores the necessity of a comprehensive usage analysis (`find_usages`) before modifying any shared code.

## What Have We Learned?
*   **Workflow Discipline:** The "Await Explicit Approval" and "Archive the Approved Plan" steps are critical and must be enforced more strictly. The agent needs to be more diligent in adhering to the sequential nature of the workflow. The repeated failure on POV-96 highlights that simply acknowledging the process is not enough; a stricter internal enforcement mechanism is required to prevent deviation.
*   **The Application Standard is Law:** Before implementing new UI features, the agent *must* analyze the existing implementation (e.g., `admin.js`) to understand the established patterns for form submission and user feedback. Deviating from the standard (e.g., using server-side redirects when the standard is AJAX) leads to rework.
*   **Reactive Programming Pitfalls:** Blocking calls (like database queries) must *never* be made directly on an IO thread in a reactive context. All such calls must be explicitly offloaded to a worker thread using mechanisms like `runSubscriptionOn`. The `BlockingOperationNotAllowedException` is a hard failure that must be addressed at the design stage.
*   **Usage Analysis is Non-Negotiable:** Modifying any shared utility class (like `ViewUtils`) without first running a `find_usages` is a critical error. The impact on all call sites must be understood *before* the change is made to prevent cascading failures.
*   **The Refactoring Checklist is Critical:** I must be more diligent in following the "Declaration, Usages, Tests" checklist. A `find_usages` on the `GenAiPool` constructor would have revealed the spike test usage and prevented the second round of test failures.
*   **Mocking is Part of the Contract:** When testing, mocks must be configured to satisfy the full contract of the object they are replacing, including simple getter methods like `getName()`.

## Action Items
*   **Agent Protocol Update:** The `AGENT.md` protocol must be updated to make `find_usages` a mandatory first step for any modification or removal of existing code. This "Usage Analysis Mandate" must be a hard requirement before a plan can even be proposed.
*   **Agent Protocol Update:** The protocol must be updated to explicitly require analyzing existing client-side code (e.g., relevant `.js` files) when implementing UI-related changes to ensure adherence to established patterns. (Implemented in v0.9.0 release task).
