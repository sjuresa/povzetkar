# Version 0.17.0 Retrospective: Administrative Control & User Onboarding

**Status:** Draft (work-in-progress; finalize in Phase 3.1)
**Date:** TBD (set on version finalization)

## 1. Overview
v0.17.0 establishes operational governance over the platform: first-class Admin User Management, an explicit Account Activation State Machine to gate uncontrolled sign-up, and live job control (restart + audit trail; cancel deferred). Two long-standing fragility points — transcript IP rate-limiting and the "glitch in the matrix" session-expiry experience — are addressed in the same cycle.

---

## 2. Planning Phase Observations
- **Hardening Deferral:** The original roadmap bundled Admin Center with Hardening (DAST, Grafana alerts, full-text search). Scope was compressed at planning time to preserve execution quality; Hardening moved to v0.18.0.
- **Email Deferral:** User Approval workflow originally considered SMTP-driven notification but was descoped on discovering no SMTP infrastructure exists in the project. Approval discovery falls back to admin sidebar badge.
- **Cancel Deferral (POV-188):** Job cancel was in original scope but deferred after codebase audit revealed `executeJobLifecycle` would overwrite any `CANCELLED` status with `COMPLETED` — making cancel without a signal mechanism an illusion rather than a feature.
- **Spike-In-Task Pattern:** POV-189 (Transcript Multi-Provider) includes a built-in spike phase for Supadata API exploration rather than a separate spike POV — abstraction design is naturally entangled with the pilot integration.
- **Refactor Discipline:** OrchestrationManager → OrchestrationService rename was evaluated and rejected. Class is a true coordinator of six leaf services; "Manager" carries useful semantic distinction.
- **Planning Process Quality (see §4):** First-pass planning artifacts contained factual errors discovered only during a second interview round with codebase reading. A PPP amendment (§2.5 Pre-Interview Codebase Audit) was introduced to prevent recurrence.

## 4. What Could Be Improved?

### Planning: First-Pass Artifacts Without Codebase Reading

The initial planning session (2026-05-20) produced task definitions and a planning-process.md that contained several factual errors, all caused by the same root issue: **planning artifacts were written based on assumed codebase state rather than observed codebase state.**

Specific errors discovered during a second interview round (2026-05-21) with deliberate source-file reading:

| Artifact | First-pass assumption | Reality (from code) |
|:---|:---|:---|
| POV-186 scope | "4 call-sites" | 8 call-sites total; 5 with plugins, 3 without — different security posture |
| POV-187 redirect target | "`/login?returnTo=…`" | No `/login` SPA route exists; auth is full-page OAuth redirect |
| POV-188 cancel | "writes stop-signal, loop checks it" | `executeJobLifecycle` overwrites any status with `COMPLETED` on finish |
| POV-187 ADR | None written | Architectural decision (sessionStorage vs OAuth state) warranted an ADR |
| Ops Rollback (POV-185) | "`account.approval.required=false` flag" | ADR-0008 explicitly rejects a config flag |

**Impact:** One commit was reverted. Approximately 2h of correction work in a second session.

**Root cause:** The planning interview was conducted without reading the relevant source files first. This is analogous to writing a test without reading the code under test — plausible-sounding but not grounded.

**Fix applied:** PPP §2.5 Pre-Interview Codebase Audit (added 2026-05-21). See that section for the concrete protocol.

## 7. Action Items for Future Versions
- **SMTP Infrastructure:** Build foundational SMTP integration (dev server like Mailpit, production provider, template engine) — candidate for v0.18.0.
- **Email Notifications for Approval:** Once SMTP exists, add admin-notification email on new pending user and user-notification on approve/reject.
- **Quota-Aware Provider Routing:** v0.17.0 uses simple ordered fallback. After quota tracking has produced data, design a smart-routing policy that prefers cheapest available provider per-fetch.
- **Transcript Cache Layer:** A `transcript_cache` table keyed on video URL would eliminate redundant fetches across orchestration runs. Recognized in [ADR-0009](../adr/0009-multi-provider-transcript-strategy.md) as orthogonal to multi-provider work.
