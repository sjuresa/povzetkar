# Version 0.17.0 Retrospective: Administrative Control & User Onboarding

**Status:** Draft (work-in-progress; finalize in Phase 3.1)
**Date:** TBD (set on version finalization)

## 1. Overview
v0.17.0 establishes operational governance over the platform: first-class Admin User Management, an explicit Account Activation State Machine to gate uncontrolled sign-up, and live job control (restart + audit trail; cancel deferred). Two long-standing fragility points — transcript IP rate-limiting and the "glitch in the matrix" session-expiry experience — are addressed in the same cycle.

---

## 2. Planning Phase Observations
- **Hardening Deferral:** The original roadmap bundled Admin Center with Hardening (DAST, Grafana alerts, full-text search). Scope was compressed at planning time to preserve execution quality; Hardening moved to v0.18.0.
- **Email Deferral:** User Approval workflow originally considered SMTP-driven notification but was descoped on discovering no SMTP infrastructure exists in the project. Approval discovery falls back to admin sidebar badge.
- **Cancel Deferral (POV-188):** Job cancel was in original scope but deferred after codebase audit revealed `executeJobLifecycle` would overwrite any `CANCELLED` status with `COMPLETED` — making cancel without a signal mechanism an illusion rather than a feature.
- **Spike-In-Task Pattern:** POV-189 (Transcript Multi-Provider) includes a built-in spike phase for Supadata API exploration rather than a separate spike POV — abstraction design is naturally entangled with the pilot integration.
- **Refactor Discipline:** OrchestrationManager → OrchestrationService rename was evaluated and rejected. Class is a true coordinator of six leaf services; "Manager" carries useful semantic distinction.
- **Planning Process Quality (see §4):** First-pass planning artifacts contained factual errors discovered only during a second interview round with codebase reading. A PPP amendment (§2.5 Pre-Interview Codebase Audit) was introduced to prevent recurrence.

## 4. What Could Be Improved?

### Planning: First-Pass Artifacts Without Codebase Reading

The initial planning session (2026-05-20) produced task definitions and a planning-process.md that contained several factual errors, all caused by the same root issue: **planning artifacts were written based on assumed codebase state rather than observed codebase state.**

Specific errors discovered during a second interview round (2026-05-21) with deliberate source-file reading:

| Artifact | First-pass assumption | Reality (from code) |
|:---|:---|:---|
| POV-186 scope | "4 call-sites" | 8 call-sites total; 5 with plugins, 3 without — different security posture |
| POV-187 redirect target | "`/login?returnTo=…`" | No `/login` SPA route exists; auth is full-page OAuth redirect |
| POV-188 cancel | "writes stop-signal, loop checks it" | `executeJobLifecycle` overwrites any status with `COMPLETED` on finish |
| POV-187 ADR | None written | Architectural decision (sessionStorage vs OAuth state) warranted an ADR |
| Ops Rollback (POV-185) | "`account.approval.required=false` flag" | ADR-0008 explicitly rejects a config flag |

**Impact:** One commit was reverted. Approximately 2h of correction work in a second session.

**Root cause:** The planning interview was conducted without reading the relevant source files first. This is analogous to writing a test without reading the code under test — plausible-sounding but not grounded.

**Fix applied:** PPP §2.5 Pre-Interview Codebase Audit (added 2026-05-21). See that section for the concrete protocol.

### POV-186: External Links Open in New Tab (2026-05-23)

- **`[plugin, options]` tuple syntax**: `react-markdown`'s `rehypePlugins` prop expects plugins with options as a `[plugin, options]` tuple, not `plugin(options)` called inline. Calling `rehypeExternalLinks({...})` invokes the plugin factory at render time and passes the return value (which may be `undefined`) as the plugin — causing a runtime error. The correct form is `[rehypeExternalLinks, { target: '_blank', rel: [...] }]` passed as an element of the `rehypePlugins` array.
- **Plugin ordering is a security constraint, not a convention**: `rehypeSanitize` strips any attribute it doesn't recognize. Running `rehypeExternalLinks` before sanitize means `target` and `rel` get stripped on every render, silently producing no effect. Always: `rehypeRaw → rehypeSanitize → rehypeExternalLinks`.

## 5. Technical Observations (Post-Implementation)

### POV-185: Account Activation State Machine (2026-05-22–23)

- **Socratic interview pattern** (15 design decisions resolved one-at-a-time before any code) produced a plan with zero mid-execution reversals. Every architectural choice was grounded in codebase evidence read during the interview.
- **Compiler-enforced cleanup**: Removing `User.active` immediately surfaced all callers at compile time — no grepping for stale references needed. The `boolean` → `AccountStatus` migration was mechanically verifiable.
- **`BaseApiResource.getContentViewingUser()`** delegation helper kept call-site changes to a single line each (10 call-sites updated in under 5 minutes). Centralizing the demo-vs-real decision in `UserContextService` meant zero duplicated logic.
- **`@Authenticated` vs `@RolesAllowed`**: The distinction matters for `/me` — without it, pending/disabled users would get 403 on the very endpoint needed to show them their account status. Worth documenting explicitly.
- **V3 migration compatibility**: V3 uses `active` column directly in SQL. V30 drops it after V3 runs — safe on all environments because Flyway runs sequentially. No Java migration was needed to update V3.
- **`Map.of()` limit**: Remembered to verify `Map.of()` supports up to 10 entries before adding a 3rd role. Would have been a silent runtime error if overlooked.

### POV-185: Code Review Cycle (2026-05-23)

The initial implementation triggered 10 rounds of PR review fixes. Key lessons:

- **HTTP concerns belong in the resource layer**: The first implementation placed `checkOptimisticLock()` inside `UserAccountService`, which violated the service/resource separation. Reviewer caught it correctly. The fix — moving ETag parsing to `BaseApiResource`, changing service actions to accept a pre-loaded `User` via `load()` — was clean but required updating all four action methods plus the test layer.
- **Flyway checksum immutability is absolute**: After adding a `version` column to V32's INSERT, running the app immediately produced "Migrations have failed validation" because V32 was already applied in the dev environment. No in-place edits to applied migrations are possible; a separate V33 was required. Lesson: treat applied migrations as read-only the moment a dev environment runs them — even during the same task.
- **`@Version` increments on every merge**: `setUserStatus()` in `UserApiResourceTest` directly updated `accountStatus` via `em.merge()`. This incremented `@Version`, causing subsequent action tests to fail with 409 when they sent the pre-update version. Fixed by returning the new version from `setUserStatus()` and using it in the test header.
- **Scope backfill migrations correctly**: V33 initially backfilled only the demo user's `version`. Reviewer correctly noted that any user created before the `@Version` column was added (via V30) would also have `version IS NULL`. Broadened to `UPDATE users SET version = 0 WHERE version IS NULL`.
- **AtomicLong double-checked locking for singleton caches**: `UserContextService` is `@ApplicationScoped` — a single instance per JVM, but under concurrent requests. Replacing `volatile Long` with `AtomicLong(0)` (0 = uninitialised, -1 = not found) with a `synchronized` inner block for the first-write path provides correct lazy initialisation without holding a lock on every read.
- **Weak ETag prefix stripping**: Some HTTP clients send `W/"version"` (weak ETag). `BaseApiResource.checkOptimisticLock()` strips `W/` and quotes before parsing to avoid spurious 409 errors from compliant clients.
- **SonarJS as a lint gate**: Adding `eslint-plugin-sonarjs` surfaced several code-smell violations in the same pass (unused variables, cognitive complexity, duplicate literals). Worth adding at the beginning of a feature, not retroactively during review.

### POV-188: Background Job Dashboard (2026-05-23)

- **`@TestSecurity` + `getAuthenticatedUser()` require a matching DB row**: `@TestSecurity(user = "admin")` sets the principal name to `"admin"`, but `UserContextService.getCurrentUser()` resolves the User entity by looking up `username = "admin"` in the DB. Without a matching row, the call throws and the endpoint returns 401 — not 403. The fix is a `@BeforeEach` that upserts the test user. This is documented in `UserApiResourceTest` but easy to miss when adding new endpoints that call `getAuthenticatedUser()` to an existing test class.
- **Codegen is always the right answer**: An early instinct to manually edit the generated `GetApiV1AdminJobsParams` type was correctly challenged. The project has a clean `mvn package → gen:api` pipeline and `openapi.json` is always present in `backend/target/` — use it. Manual edits to generated files create drift that the next codegen run silently overwrites.
- **`FilterBuilder` scales cleanly**: Replacing the `if/else` branching in `getJobList()` with `FilterBuilder` to support 2 filters cost one extra line and eliminated a 2×2 conditional matrix. Worth doing proactively whenever a method gets a second filter parameter.
- **Sonar `no-nested-conditional` in JSX**: The `isLoading ? X : count === 0 ? Y : Z` ternary pattern triggers `sonarjs/no-nested-conditional`. The fix is to replace with three independent `{condition && <Element />}` expressions — cleaner and more readable anyway.

### POV-187: Session Expiry Handling (2026-05-23)

- **Planning interview revealed a better architecture**: The original ADR-0010 proposed `sessionStorage` + landing page banner + manual Sign In click. During the interview, exploring `LoginResource.java` revealed it already accepts a `?redirect=<path>` param and validates it safely via `resolveSafeDestination()`. This made `sessionStorage` entirely unnecessary. The insight came from reading the backend code during the interview — not from the planning artifact.
- **Auto-login is superior to manual re-auth**: If the user's Google session is still active (typical), the OAuth round-trip completes invisibly in under a second. The user is returned to their original page with zero friction. Always consider whether the user actually needs to see the landing page at all.
- **`router.state.location.searchStr` not `search`**: TanStack Router's `ParsedLocation.search` is a parsed object — stringifying it produces `[object Object]`. The raw query string lives on `searchStr`. Worth checking the type definitions before assuming string behaviour.
- **Never-resolving promise pattern for navigation interception**: After `window.location.href = ...`, the current JS execution continues until the browser begins navigation. A `return new Promise(() => {})` after the redirect assignment prevents the error from propagating to React's error boundary during the brief window before navigation takes over.
