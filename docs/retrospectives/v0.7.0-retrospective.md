# Retrospective for Version 0.7.0

**Status:** Draft / In Progress
**Date:** 2026-01-08

## Preliminary Notes from Planning

*   **Operational Excellence Focus:** This version explicitly prioritizes stability and tooling over new user features, addressing the "process debt" identified in v0.6.2.
*   **Technical Migration:** The migration to Quarkus 3.x is a significant technical undertaking done upfront to avoid debt accumulation.
*   **Iterative Planning:** The definition of Task 4 (Admin UI) evolved significantly during the planning phase to include backend persistence (Error Codes, Transcripts). This ensures the UI is backed by actual data rather than just being a cosmetic update.

## What Went Well?

*   (Capture items as they happen)
*   **Proactive Complexity Discovery:** We identified significant complexity in the "Time Period Briefings" (Context Window limits) and "Rate Limiting" (TPM/Quotas) tasks *during* the planning review. This allowed us to adjust estimates and designs before writing code, preventing likely failures mid-sprint.
*   **Strategic Prioritization:** We made a conscious decision to descale v0.7.0 by deferring features to v0.9, prioritizing the architectural goal of Standalone Deployment (v0.8). This prevents "feature creep" and maintains momentum on the critical path.
*   **Automated Framework Upgrade:** Using the `quarkus update` command was highly effective for the initial migration from 3.15.6 to 3.27.1. It correctly identified and replaced deprecated dependencies like `quarkus-resteasy-reactive-jackson` with `quarkus-rest-jackson`.
*   **TDD for Orchestration Resilience:** The TDD approach for handling stuck `PENDING` items (POV-82) was highly effective. Writing the failing test first provided a clear target and immediately validated that the fix worked as intended.
*   **Incremental UI Feedback:** The iterative process of fixing the UI for granular orchestration (POV-83) was effective. The test failures and user feedback quickly pinpointed the exact issue (QueryParam vs. FormParam vs. JavaScript behavior), leading to a robust solution.

## What Didn't Go Well?

*   (Capture items as they happen)
*   **Test Failures After Upgrade:** The automated upgrade led to critical test failures (`NoSuchMethodError`). This was caused by explicit version management of `JUnit` and `Mockito` in the `pom.xml`, which conflicted with the versions expected by the new Quarkus BOM.
*   **Reactive Logging:** The initial implementation of the logging improvement for POV-82 was approached as a simple string change. However, this overlooks the fact that logging occurs within different services (`YouTubeSummarizationStrategy`) which may not have access to all the desired data (like `formattedDuration` from `YouTubeVideo`) without it being passed down through several layers.
*   **Qute Template Parsing:** A subtle Qute parsing error (`{! ... }` being a comment) caused a build failure. This was a "gotcha" that was not immediately obvious and required knowledge of the template engine's specific syntax.
*   **Incorrect Assumption about Form Submission:** The initial fix for the granular orchestration UI was incorrect because I assumed a standard form POST, overlooking the fact that a JavaScript file was intercepting the submission and sending query parameters. This led to rework.
*   **Catastrophic Failure on POV-84:** The implementation of error and transcript persistence was a complete failure. Multiple attempts to fix test failures resulted in a loop of introducing new bugs. The core issue was an overly complex design involving multiple, nested transactions and incorrect state management of detached entities. The attempts to fix this incrementally only made the code more brittle and harder to reason about, leading to a state where the task had to be reverted entirely.

## What Have We Learned?

*   (Capture items as they happen)
*   **Trust the BOM:** For core and testing libraries, it is crucial to let the Quarkus BOM manage dependency versions. Overriding them, even if they seem correct, creates a high risk of classpath conflicts during framework upgrades. The `quarkus update` tool is not a silver bullet and requires manual verification of the resulting `pom.xml`.
*   **Logging is a Cross-Cutting Concern:** Improving observability is not just about changing a log line. It requires thinking about data flow. To have rich, contextual logs, the necessary data must be available at the point of logging. This might require passing objects down the call stack, which should be considered in the initial design. A standardized logging approach (as noted in the backlog) would mitigate this.
*   **Always Verify Client-Side Behavior:** When fixing UI-related API issues, always check for client-side JavaScript that might be altering the request. The browser's developer tools are the source of truth, not just the HTML form definition.
*   **Complexity is a Red Flag:** The repeated failures on POV-84 were a direct result of a flawed, complex design. When a task requires multiple nested transactions and complex state-passing of detached entities, the design is wrong. The correct pattern is to simplify: fetch data, process it, and then write the result in a single, atomic transaction per logical outcome. A task that becomes this difficult to test is a sign that it needs to be broken down into smaller, more manageable pieces.
