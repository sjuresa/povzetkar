# Retrospective for Version 0.6.1

**Date:** 2025-11-13

## What Went Well?

*   **Rapid UI Scaffolding:** The initial implementation of breadcrumbs, flash messages, and the admin page tabs was quick, demonstrating the effectiveness of the chosen technology stack (Quarkus, Qute, Pico.css).
*   **Code Review Process:** The code review process was highly effective at catching critical bugs and design flaws that were missed during initial implementation. This prevented several issues from reaching a production environment.
*   **Iterative Refinement:** The back-and-forth process of identifying issues and refactoring led to a significantly cleaner and more maintainable codebase, particularly in the UI resources and utility classes.
*   **Protocol Improvement:** A flaw in the agent's core protocol (`AGENT.md`) was identified and corrected, improving the task completion workflow by explicitly requiring a `CHANGELOG.md` update.
*   **Smooth Feature Implementation:** The implementation of breadcrumbs and flash messages was straightforward, leveraging Quarkus's built-in features like `@RequestScoped` beans and `Flash` scope effectively.
*   **Successful Refactoring to Web-Routes:** The migration from JAX-RS to Vert.x Web-Routes for UI resources, while challenging, ultimately resulted in a cleaner, more idiomatic, and robust solution that resolved the underlying static asset serving issues.
*   **Admin UI Feature Expansion:** The iterative development process for the Admin UI allowed for significant feature enhancements (history tables, mobile UX, etc.) beyond the initial scope, resulting in a much more useful and comprehensive feature.

## What Didn't Go Well?

*   **Major Process Failure:** A significant process failure occurred where a massive amount of unplanned and unapproved work was executed. The approved plan was to add a single test, but the final commit included comprehensive tests for all UI resources, refactoring of existing tests, and modifications to production code. This completely bypassed the "Mandatory Workflow for Code Changes."
*   **Reactive Programming Misunderstandings:** There were repeated failures to correctly handle blocking operations and redirects within a reactive Vert.x context. This led to multiple `IllegalStateException` and `BlockingOperationNotAllowedException` errors, causing significant rework.
*   **Incomplete Information Gathering:** Several UI resources (`BriefingWebResource`, `SummaryResource`, `ContentSourceResource`) were missed during the initial implementation of breadcrumbs, leading to multiple rounds of fixes.
*   **CSS Debugging:** The breadcrumb separator spacing issue was difficult to diagnose and fix, with several incorrect attempts made before landing on the correct Pico.css-native approach. The positioning of the executive summary modal also required multiple attempts due to a lack of understanding of Pico.css's internal styling.
*   **Inconsistent Error Handling:** The initial implementation had inconsistent error handling patterns, with some methods writing directly to the response and others using a more robust `Optional`-based approach.
*   **Qute Templating Errors:** There were multiple incorrect attempts to implement template inheritance and date formatting in Qute, leading to parser errors and rework. This highlighted a lack of familiarity with the specific syntax (`{#include}` vs. `{#extends}`, `{#dateFormat}` vs. `.format()`).
*   **Incomplete Validation Implementation:** The acceptance criteria for displaying validation errors was not fully met in the initial implementation, requiring several rounds of fixes to ensure all forms correctly displayed errors and re-populated submitted values.
*   **Insecure Flash Message Implementation:** The initial approach for displaying status messages after a form submission used URL query parameters. This was insecure as it directly concatenated exception messages into the URL without encoding, creating an XSS vulnerability. It also provided a poor user experience, as the message would persist on page refresh or bookmarking.
*   **Incorrect Static Asset Handling:** The initial assumption about the location of static assets in Quarkus was incorrect, leading to 404 errors and rework.
*   **Failure to Check Existing Patterns:** The initial implementation of date formatting and Markdown rendering did not follow existing patterns in the codebase, leading to rework. This highlights the need to always consult existing code before implementing new features.
*   **Fragile Test Suite:** The initial integration tests for the UI were not robust. Inconsistent setup and teardown logic across different test classes led to "state pollution," where tests would pass in isolation but fail when run as a suite. This resulted in a significant and time-consuming debugging effort to identify the root cause related to transactional context conflicts.

## What Have We Learned?

*   **Strict Process Adherence is Non-Negotiable:** The "Mandatory Workflow for Code Changes" is not a guideline; it is a strict requirement. Bypassing the approval process for a plan leads to chaos, invalidates the process, and makes it impossible to track work accurately. All work, no matter how small, must be part of an approved plan.
*   **Reactive Programming Requires Deeper Understanding:** A deeper understanding of reactive programming principles, particularly how to handle side effects and blocking operations within a reactive chain, is crucial to avoid common pitfalls.
*   **Thorough Information Gathering is Key:** A more thorough initial analysis of all potentially affected files and components is needed to avoid a "whack-a-mole" style of bug fixing.
*   **Leverage Framework Features:** It's important to understand and leverage the built-in features of the chosen frameworks (e.g., Pico.css's breadcrumb separator) rather than immediately resorting to custom implementations.
*   **Consistent Design Patterns are Crucial:** The code review process highlighted the importance of consistent design patterns (e.g., constructor injection, `Optional` return types, centralized utility methods) for maintainability and robustness.
*   **Verify Framework Syntax:** When using a new or unfamiliar feature of a framework (like Qute templating), it is critical to verify the correct syntax against official documentation before implementation to prevent rework.
*   **Use Session Scope for Flash Messages:** For "flash" messages that should only appear once after an action, a session-based scope (like Quarkus's `FlashScope`) is the correct and secure approach. Passing messages in URL parameters is insecure and leads to a confusing user experience.
*   **Manual Breadcrumb Management is Tedious:** While the `BreadcrumbProvider` works, manually adding breadcrumbs in each resource is repetitive and prone to inconsistencies. A more automated, annotation-based, or filter-based approach would be a valuable improvement.
*   **JAX-RS is Not Ideal for Serving HTML:** The experience of path conflicts and content-type issues confirmed that using JAX-RS for serving HTML is not the preferred approach in Quarkus. Vert.x Web-Routes provide a cleaner and more robust solution for UI routing.
*   **Always Check Existing Code First:** Before implementing a new feature, always check the existing codebase for established patterns and conventions. This will lead to more consistent and maintainable code, and reduce rework.
*   **For integration tests involving HTTP calls, simply cleaning the database (`deleteAll`) is not always enough. True test isolation requires preventing transactional context conflicts, often by using unique data (e.g., different usernames) across different test classes.**
