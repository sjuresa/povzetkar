## 1. What was done

Three build/test-tool upgrades, one cause per commit (plan P1):

**`source-map-js` 1.2.1 → 1.2.2** (commit 1, `566ffb6f`): `npm update source-map-js`, lockfile only — one entry
changed; `npm ls` shows 1.2.2 under `@tailwindcss/node`, `postcss` and `magicast`. Fixes HIGH GHSA-68fv-2mgg-jv7q.

**Vitest and `@vitest/coverage-v8` 3.2.7 → 5.0.3** (commit 2, `63da55ac`) on the existing Vite 6.4.3 (no change to
`overrides.vite`; `npm ls` shows a single `vite@6.4.3`). Fixes `tinypool` CRITICAL (GHSA-5gmw-xhrv-c9v3,
GHSA-85c8-ppgw-ccpr) and `@vitest/mocker` MODERATE (GHSA-82fw-gwwq-j7x9).
- Vitest 5's default `clearMocks: true` (verified in `node_modules/vitest/dist/config.cjs:56`) replaces the 12
  hand-written `vi.clearAllMocks()` calls (plan P2); four hooks that became empty and their unused
  `beforeEach`/`afterEach` imports are gone. No test needed a fix — 149/149 at the first run. After review round 2
  the default is stated in `vite.config.ts` (`clearMocks: true`), and the last leftovers of the old patterns are gone
  (`ExportMenu.test.tsx`'s own Jest-flavoured jest-dom import, a `mockClear()` in `DashboardPage.test.tsx`).
- Type check (not foreseen by the plan): `tsc -b` failed with ~100 errors in test files while the tests were green
  (Vitest does not type-check). `src/test/setup.ts` imported the Jest flavour of jest-dom (augments the global
  `jest.Matchers`, which Vitest 3 picked up through Jest-compat types removed in Vitest 4) → now
  `@testing-library/jest-dom/vitest`; `useJobEvents.test.ts` used Node's `global`, whose types no longer reach the app
  project → `globalThis`. The `vitest/config` type reference the plan held in reserve was not needed.

**orval 8.5.3 → 8.41.0, exact pin** (commit 3), API client regenerated per RUNBOOK §8.3 (`./mvnw package
-DskipTests -pl backend -am`, `npm run gen:api`). Fixes the orval CRITICAL chain (11 critical + 1 high advisory) and
the HIGH transitive `@orval/*`, `js-yaml`, `braces`, `micromatch`, `fast-glob`, `globby` (IDs in CHANGELOG). No
react-query-v4 fallback. 83 files, +1615 / −1106 — identical in size to the Brainstorm exploration. No hand edits;
one call-site change (Behaviour 4). `package.json` overrides: `esbuild ^0.25.0` removed — a security floor
(GHSA-67mh-4wv8-2f99, `f83274e3`) that, as a caret on 0.x, also capped orval below the esbuild `^0.28.0` that
`@orval/core@8.41.0` requires; Vite 6.4.3 keeps esbuild 0.25.12 by its own range, orval gets 0.28.2, both above the
floor. `glob ^11.0.1` removed — no package depends on glob since Vitest 3 left (`npm ls glob` empty). Diff by
category:
- *Format:* header `Generated by orval v8.5.3` → `Generated by orval` (all 82 changed files; model files change only
  there, except `model/index.ts`, which also gains a final newline), whitespace, JSDoc moved from the response type to
  the request function.
- *New file:* `src/api/generated/index.ts`, a barrel re-exporting the 13 tag modules; nothing imports it. Kept as
  generator output — `indexFiles: false` would also drop `model/index.ts`, which the app imports.
- *Types (additive or equivalent):* request options `RequestInit` → `Parameters<typeof customInstance>[1]` (the
  mutator's own `CustomRequestOptions`); new `get…MutationKey()` functions and `…MutationVariables` types; mutation key
  built by that function (same value).
- *Behaviour 1 — `withQueryKey`:* query hooks return the result through property getters instead of
  `{ ...query, queryKey }`. TanStack Query tracks which result properties a component reads (`trackResult` proxy,
  `queryObserver.ts:331-342`) and notifies only on changes to those (`:753-779`); the spread read every property, so
  every change re-rendered. Effect: fewer re-renders, same data. No `notifyOnChangeProps` in the app.
- *Behaviour 2 — exploded array params:* `sort` (6 param models) and `status` (content items) are sent as repeated
  keys (`sort=a&sort=b`) instead of `toString()` (`sort=a,b`); `toString()` → `String()` for scalar values (same
  result). All callers pass one element — `sort` in `AdminJobsPage.tsx:27`, `UsersPage.tsx:23`,
  `ContentManagementPage.tsx:27`, `status` from `ContentItemFilters.tsx:39` — → identical URLs.
- *Behaviour 3 — request headers (not named in the plan):* body-carrying requests merge `options.headers` through a
  `getHeaders` helper that also accepts a `Headers` object or header pairs (the old object spread dropped those;
  body-less requests pass `options` through, and `customInstance` already normalised them). No caller passes headers
  to a body-carrying request — the only caller with headers, `UsersTable.tsx:94` (`If-Match`), calls body-less POSTs
  → unchanged. (Corrected after review round 2, which found the first version of this check on the wrong code path.)
- *Behaviour 4 — query guard (found by review round 2):* the 13 id-keyed detail hooks are disabled only for a
  `null`/`undefined` id (`id !== null && id !== undefined`) instead of any falsy one (`!!(id)`), so `0`, `NaN` and `''`
  now send requests. Callers: `BriefingDetailPage`, `JobAuditModal`, `SummaryModal`, `ExportMenu` and
  `QuickSourceIntake` set their own `enabled`; `PublicResolverPage`'s `uuid` is a required route segment. Only
  `SourceDetailPage` relied on the generated guard — `/sources/abc` would have sent `GET /api/v1/sources/NaN`. It now
  sets `enabled: id > 0` — like the old guard for `NaN` and `0`, and stricter for negative ids, which the old guard
  fetched (`!!(-1)`; the backend answered 404, the page showed "Source not found" either way); two new tests pin it
  (enabled for `5`, disabled for `abc`).

**Documentation:** RUNBOOK §8.3 (pin 8.41.0, header without version); backlog — orval entry removed (done),
