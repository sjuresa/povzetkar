This document lists the concrete tasks for migrating the project to version 0.5. **This version is strictly focused on establishing the foundational "architectural skeleton" of the new Quarkus application**, as originally defined in the [`roadmap.md`](../overview/roadmap.md). It prepares the project for the incremental migration of features in subsequent versions (v0.6, v0.7, etc.).

The "Strangler Fig" migration pattern will be employed, and the **first concrete "strangling" step** (delegating author fetching) will be completed in this version.

### **Task 1 [POV-47]: Foundational Quarkus App & DB Setup**

**Title:** `chore(quarkus): Create foundational Quarkus app and database setup`

**Description:**
This task establishes the new Quarkus application's skeleton. It includes creating the project structure, converting the `pom.xml`, and setting up the Docker environment for the database.

**Acceptance Criteria:**
- A new Quarkus project is created in a subdirectory (e.g., `quarkus-app/`).
- The root `pom.xml` is converted to a multi-module build, with the old application in one module and the new `quarkus-app` in another.
- The `quarkus-app/pom.xml` is configured with the Quarkus BOM and initial dependencies: `quarkus-resteasy-reactive-jackson`, `quarkus-hibernate-orm-panache`, and `quarkus-jdbc-postgresql`.
- A `docker-compose.yml` is created to run a PostgreSQL database.

### **Task 2 [POV-48]: Health Check & Initial Integration Test**

**Title:** `test(quarkus): Implement health check and DB connectivity test`

**Description:**
This task verifies that the foundational setup is working correctly by creating a simple health check endpoint and a robust integration test that confirms database connectivity.

**Acceptance Criteria:**
- A simple health check endpoint (e.g., `GET /q/health`) is created and is working.
- **A `@QuarkusTest` integration test is created. It must successfully start the Quarkus application and connect to a Testcontainers-managed PostgreSQL database, proving the entire stack is configured correctly.**

---

### **Task 3 [POV-49]: Implement Core Data Entities**

**Title:** `feat(model): Create core JPA entities including Topic support`

**Description:**
This task creates the initial JPA entities based on [`04_database_design.md`](../sdlc/04_database_design.md). These entities will serve as the data model for all subsequent features.

**Acceptance Criteria:**
- A `Channel` JPA entity is created to store monitored channel IDs and names.
- A `Topic` JPA entity is created.
- A many-to-many relationship is defined between `Topic` and `Channel`.
- A `ContentItem` JPA entity is created. It must include the `processing_status` field as defined in the database design.
- **Unit tests are created for each entity to verify basic constraints and default values.**

---

### **Task 4 [POV-50]: Create Data Migration Script**

**Title:** `chore(quarkus): Create one-time script to migrate topics and channels`

**Description:**
A simple, one-time migration script will be created to populate the new PostgreSQL database with the initial set of topics and their associated channels from the `authors_to_query.txt` files. This script will be a standalone utility (e.g., a Java `main` class with a JDBC dependency) and will not interact with any APIs. It is designed to be run once and then discarded.

**Acceptance Criteria:**
- A standalone script/class `DatabaseMigrator` is created.
- It connects directly to the PostgreSQL database using JDBC.
- It creates records for each topic (e.g., "ai", "crypto") in the `topics` table.
- It reads the respective `authors_to_query.txt` files for each topic, inserts the data into the `channels` table, and creates the relationships in the `channel_topic` join table.

### **Task 5 [POV-51]: Vertical Slice Validation API**

**Title:** `feat(quarkus): Implement topic-aware API for listing channels`

**Description:**
This task creates a meaningful, non-throwaway vertical slice that provides immediate value. It validates the entire architectural stack by serving the data migrated in the previous step.

**Acceptance Criteria:**
- A JAX-RS resource (`ChannelResource.java`) is created.
- It exposes a single, read-only endpoint: `GET /api/v1/topics/{name}/channels`. The response should be a JSON array of objects, each containing at least the channel ID.
- **`@QuarkusTest` integration tests are written to verify the endpoint against a Testcontainer database.** The test should confirm that the API correctly returns the data populated by the migration script.

---
### **Task 6 [POV-52]: Refactor Legacy AuthorService**

**Title:** `refactor(legacy): Delegate author fetching to new Quarkus API`

**Description:**
This is the first "strangling" step. The existing `AuthorService` will be refactored to replace its file-reading logic with a call to the new Quarkus API. **Crucially, the responsibility for enriching channel IDs with details via `YouTubeDataService` will remain within the legacy `AuthorService` for this version.**

**Acceptance Criteria:**
- A REST client dependency (e.g., `java.net.http.HttpClient` or a library) is added to the legacy application's Maven module.
- The `getAuthorsWithDetails` method in the legacy `AuthorService` is modified.
- The new implementation calls the `GET /api/v1/topics/{name}/channels` endpoint on the Quarkus application to get a list of channel IDs.
- The logic for reading `authors_to_query.txt` is completely removed from `AuthorService`.
- The service continues to call `youtubeDataService.getAuthorDetails` for each channel ID received from the new API.
- The method signature and return type (`List<Author>`) remain unchanged to avoid breaking changes in its caller (`Povzetkar.java`).
