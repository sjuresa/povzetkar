This document lists the concrete tasks for migrating the project to version 0.5. **This version is strictly focused on establishing the foundational "architectural skeleton" of the new Quarkus application**, as originally defined in the `roadmap.md`. It prepares the project for the incremental migration of features in subsequent versions (v0.6, v0.7, etc.).

The "Strangler Fig" migration pattern will be employed, but the actual delegation of logic from the old application to the new one will begin in version `v0.6`.

### **Task 1 [POV-29]: Foundational Quarkus App & DB Setup**

**Title:** `chore(quarkus): Create foundational Quarkus app and database setup`

**Description:**
This task establishes the new Quarkus application's skeleton. It includes creating the project structure, converting the `pom.xml`, and setting up the Docker environment for the database.

**Acceptance Criteria:**
- A new Quarkus project is created in a subdirectory (e.g., `quarkus-app/`).
- The root `pom.xml` is converted to a multi-module build, with the old application in one module and the new `quarkus-app` in another.
- The `quarkus-app/pom.xml` is configured with the Quarkus BOM and initial dependencies: `quarkus-resteasy-reactive-jackson`, `quarkus-hibernate-orm-panache`, and `quarkus-jdbc-postgresql`.
- A `docker-compose.yml` is created to run a PostgreSQL database.

---

### **Task 2 [POV-30]: Health Check & Initial Integration Test**

**Title:** `test(quarkus): Implement health check and DB connectivity test`

**Description:**
This task verifies that the foundational setup is working correctly by creating a simple health check endpoint and a robust integration test that confirms database connectivity.

**Acceptance Criteria:**
- A simple health check endpoint (e.g., `GET /q/health`) is created and is working.
- **A `@QuarkusTest` integration test is created. It must successfully start the Quarkus application and connect to a Testcontainers-managed PostgreSQL database, proving the entire stack is configured correctly.**

---

### **Task 3 [POV-31]: Implement Core Data Entities**

**Title:** `feat(model): Create core JPA entities for Channel, Author, and ContentItem`

**Description:**
This task creates the initial JPA entities based on `04_database_design.md`. These entities will serve as the data model for all subsequent features.

**Acceptance Criteria:**
- A `Channel` JPA entity is created to store monitored channel IDs and names.
- JPA entities for `Author` and `ContentItem` are created. `ContentItem` includes a `processing_status` field (`PENDING`, `COMPLETED`, `FAILED`).
- **Unit tests are created for each entity to verify basic constraints and default values.**

---

### **Task 4 [POV-32]: Channel Management API**

**Title:** `feat(quarkus): Implement REST API for Channel management`

**Description:**
This task creates the first piece of business logic: a REST API for managing the list of monitored channels.

**Acceptance Criteria:**
- A JAX-RS resource (`ChannelResource.java`) is created.
- It exposes two endpoints:
  - `GET /api/v1/channels`: Lists all monitored channels.
  - `POST /api/v1/channels/import`: A bulk endpoint that accepts a list of channel IDs to be imported.
- **`@QuarkusTest` integration tests are written to verify both endpoints against a Testcontainer database.**

---

### **Task 5 [POV-33]: Create Data Migration Scripts**

**Title:** `chore(quarkus): Create standalone migration scripts for channels and state`

**Description:**
To ensure a clean separation, two standalone, one-time migration scripts (or simple Java `main` classes within the `quarkus-app` module) are created to import data from the old application's files into the new system via its API.

**Acceptance Criteria:**
- A new endpoint `POST /api/v1/state/import` is created in the Quarkus app to receive and persist historical state data. This endpoint will create placeholder `ContentItem` records to represent the last processed state.
- A script/class `ChannelMigrator` is created. It reads `authors_to_query.txt` and calls the `POST /api/v1/channels/import` endpoint.
- A script/class `StateMigrator` is created. It reads `processing_state.properties`, transforms the data, and calls the `POST /api/v1/state/import` endpoint.
- **The migration scripts are documented in the `RUNBOOK.md`.**
