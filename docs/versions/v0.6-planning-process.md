## 1. Overarching Goal: The Great Acceleration

The planning for version 0.6 represents a **major strategic pivot** for the project. The original, incremental plan (which focused solely on migrating state management) was superseded by a new set of requirements demanding a much faster path to a fully autonomous application.

The new, primary goal of version 0.6 is therefore to **migrate the entire core workflow**—from video fetching to Git publishing—into the Quarkus application, effectively decommissioning the legacy application's main responsibilities in a single, ambitious version.

## 2. Rationale for Key Decisions

### The Pivot from Incremental to Full Migration

The initial plan for v0.6 was a small, safe step in the "Strangler Fig" migration. However, new requirements made it clear that a faster delivery of a standalone product was a higher priority. This led to the decision to consolidate the goals of several future versions (old v0.6, v0.7, v0.8) into this new, expanded v0.6.

### Full Autonomy as the Guiding Principle

A key question during planning was how to handle the final step of Git publishing. The decision was made for the **new Quarkus application to take full ownership of this process**. This avoids creating a complex, two-way dependency where the legacy app would need to fetch the final briefing from the new app. By making the Quarkus app fully autonomous, we simplify the architecture and create a clean cut-over.

### A Logical Task Flow

The tasks in `v0.6-tasks.md` are structured to build the new application layer by layer, ensuring a logical progression and minimizing risk:
1.  **Docs First:** The first task is to align the high-level design documents. This embodies the "Roadmap Confirmation First" principle from our v0.5 retrospective, ensuring we build on a solid, agreed-upon foundation.
2.  **Data Model:** We start by extending the database schema (`Summary`, `Briefing`), as all subsequent logic depends on it.
3.  **Component Migration:** We then migrate the individual legacy services (`ChannelDetailService`, `SummarizationService`) into self-contained, testable Quarkus components.
4.  **Orchestration:** Once the "worker" components are in place, we build the "manager" (`ScheduledOrchestrator`) to control the workflow.
5.  **Final Output:** The final services for briefing generation and Git publishing are created.
6.  **Decommissioning:** The last step is the formal removal of the now-redundant legacy code.

### Introducing Multi-Tenancy

A critical mid-planning decision was to introduce the `User` entity, making the application multi-tenant from this version forward. This decision was made to align the architecture with the long-term vision of a multi-user platform.

This required modifying the `Topic` entity to be user-specific and adjusting the main `ScheduledOrchestrator` to iterate through users first, then their topics. This change, while adding complexity, ensures that the core workflow is built on a scalable, multi-tenant foundation from the outset.

### Refining Service Boundaries

Drawing lessons from our v0.5 retrospective, we paid special attention to defining clear service responsibilities upfront:
*   **`SummarizationService` is Self-Contained:** We explicitly defined that this service is responsible for its entire lifecycle, including handling all internal errors and updating the `ContentItem` status. This simplifies the orchestrator, which does not need to manage the *outcome* of each summarization. It only needs to invoke the service for each video (ideally in parallel) and **await the completion of all tasks** before proceeding with the workflow.
*   **`BriefingService` is Regenerative:** We clarified that the briefing generation process must be idempotent and regenerative. The service is designed to take a time period (e.g., a date) and generate a complete, up-to-date briefing from *all* available summaries for that period. This robustly handles scenarios where the process runs multiple times a day, ensuring the final briefing is always comprehensive.
