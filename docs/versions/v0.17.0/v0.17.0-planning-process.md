# Version 0.17.0 Planning Process: Administrative Control & User Onboarding

**Status:** Active
**Date:** 2026-05-20
**Planning Task:** POV-182

## Introduction
After v0.16.0's UX-first transformation, v0.17.0 returns the focus to **operational governance**. The platform now needs **administrative tooling** to control who enters (user approval), what is observed (job dashboard), and what is configurable (admin roles). At the same time, two long-standing fragility points — YouTube IP rate-limiting on transcript fetches, and the "glitch in the matrix" session-expiry experience — are addressed before they become user-visible failures.

The original v0.17.0 roadmap entry combined **Administrative Control** with **Hardening & Operational Excellence** (DAST, Grafana alerting, full-text search). Per the planning brainstorm (2026-05-20), Hardening has been **deferred to v0.18.0** to preserve focused execution and avoid scope dilution.

## Scope

### In Scope (Confirmed)
1. **Administrative Command Center**
   - Admin User Management UI (roles, account statuses, permissions)
   - User Approval Workflow (`PENDING_APPROVAL` account state + admin approval action)
   - Background Job Dashboard (Restart + Audit — Cancel deferred, see Discussion 7)
2. **Resilience & Polish**
   - Multi-provider transcript abstraction + Supadata pilot integration + randomized fetch delay
   - External links in summaries open in new tab (rehype-external-links)
   - Session expiry handling (401 interceptor → login redirect, ErrorPage cleanup)

### Deferred to v0.18.0 (Hardening & Operational Excellence)
- DAST integration (OWASP ZAP) into release cycle
- Grafana alerting thresholds for system health
- Specialized pg_trgm/Lucene full-text search
- Additional transcript providers (ytscribe, transcriptapi)

### Skipped (Protocol Elasticity Justifications)
- **UI/UX Manifesto:** No new design tokens. Admin UI consumes the existing Zinc palette and form patterns established in v0.16.0 (POV-178). Skipped per [PPP § 5](../../process/planning_protocol.md).
- **OrchestrationManager → OrchestrationService rename:** Evaluated and rejected. The class is a true coordinator of six leaf services; "Manager" suffix carries useful semantic distinction. Logged in [improvements.md](../../backlog/improvements.md) only if reconsidered.

### Discussion 1: Roadmap Pivot — Hardening Deferred
- **Strategic Pivot:** Original roadmap bundled Admin Center + Hardening (DAST, Grafana alerts, full-text search). User signalled scope concern during brainstorming (2026-05-20).
- **Critique:** Hardening tasks are independent from Admin Center and have different stakeholder value (security audit cadence vs. user-visible governance). Bundling risks crowding out execution quality on the user-visible work.
- **Decision:** Split into two versions. v0.17.0 = pure Administrative Control + selected resilience fixes; v0.18.0 = dedicated Hardening cycle.

### Discussion 2: User Approval Workflow — Email vs. No Email
- **Context:** New user approval is a synchronous bottleneck: admin must act before user can use the platform. Email notifications would close the loop faster.
- **Critique:** No SMTP infrastructure exists in the project. Adding SMTP (dev server like Mailpit/MailHog, production SMTP provider, template engine, retry/error handling) would inflate the task to 2–3 dev-days on its own.
- **Decision:** **No email integration in v0.17.0.** Approval visible via Admin UI badge/counter only. SMTP infrastructure is a candidate for v0.18.0 or later. Logged as an explicit decision in [ADR-0008](../../adr/0008-account-activation-state-machine.md).

### Discussion 3: Transcript Provider Strategy — Scope Compression
- **Context:** Three candidate providers were proposed (Supadata ~100/month free, ytscribe ~50/month free, transcriptapi $5/month for 1000). All three would multiply integration cost.
- **Critique:** Multi-provider abstraction can be designed without integrating all providers upfront; one pilot integration is sufficient to validate the abstraction. Adding more providers later reduces to "implement another adapter."
- **Decision:** Pilot **one provider (Supadata)** + abstraction + jitter delay on the legacy YouTube path. Remaining providers deferred to v0.18.0.

### Discussion 4: External Links in Summaries — Render-time vs. Prompt
- **Context:** Links rendered in summaries currently open in the same tab, ejecting users from the briefing context.
- **Critique:** Two implementation paths: (a) modify the AI prompt to emit `target="_blank"` markup (unreliable, costs tokens, LLM may regress), or (b) post-process at render time using `rehype-external-links` (deterministic, ~700B gzipped, zero runtime cost since the rehype pipeline is already in the bundle).
- **Decision:** **Render-time fix (frontend), scope α.** Codebase audit revealed 8 `ReactMarkdown` call-sites total — 5 already carry `[rehypeRaw, rehypeSanitize]` (BriefingDetailPage.tsx ×2, PublicBriefingView.tsx ×2, PublicSummaryView.tsx ×1); 3 do not (SummaryModal.tsx:151, SystemMetadata.tsx:189+227). Scope α adds `rehypeExternalLinks` only to the 5 with existing plugins. The 3 without plugins are a separate DRY/security backlog item (shared `<MarkdownContent>` wrapper). Plugin order: `rehypeRaw → rehypeSanitize → rehypeExternalLinks`.

### Discussion 5: ErrorPage "Glitch in the Matrix" — Interceptor Approach
- **Context:** Generic `ErrorPage.tsx` triggers on session expiry because the 401 surfaces as an uncaught exception in the error boundary. Users report a confusing "glitch in the matrix" message rather than a clear "your session expired" cue.
- **Critique:** Conflating session-state errors with application errors degrades the trust signal. Session expiry should be a normal recoverable flow, not an error state. Codebase audit revealed: (a) there is no `/login` SPA route — authentication is server-side OAuth via `globalThis.location.href = '/auth/login'`; (b) the existing `case 401` in `client.ts` already calls `clearAuth()` but re-throws, reaching the error boundary; (c) the router is an exported TanStack Router singleton, callable from the interceptor.
- **Decision:** Add 401 handling directly to the existing `case 401` in `client.ts`: store `returnTo` path in `sessionStorage`, call `clearAuth()`, navigate to `/?notice=session_expired` via `router.navigate()`. `LandingPage` consumes `sessionStorage['auth.returnTo']` after successful OAuth round-trip. See [ADR-0010](../../adr/0010-session-expiry-return-to.md).

### Discussion 6: Session Expiry — returnTo Mechanism (sessionStorage vs. OAuth State)
- **Context:** `returnTo` must survive a full OAuth round-trip (frontend → `/auth/login` → Google → callback → `/`). Two viable mechanisms: (A) `sessionStorage` bridge — store path before redirect, consume after OAuth lands back; (B) backend OAuth `state` parameter — embed `returnTo` in the OAuth state, backend redirects to it after callback.
- **Critique:** Option B is the canonical OAuth pattern and works across tabs. However, it requires non-trivial Quarkus OIDC customisation (custom `OidcAuthenticationMechanism` or `TenantResolver`) which would consume the majority of the POV-187 budget. Option A is a legitimate, widely-used SPA pattern (Auth0 SPA SDK, Firebase Auth use it). For Povzetkar's scale (closed platform, limited user base), multi-tab edge cases are negligible.
- **Decision:** **sessionStorage bridge (A) as permanent solution** — not logged as future technical debt. Replacing working code with B would deliver equivalent UX at significantly higher cost. Documented in [ADR-0010](../../adr/0010-session-expiry-return-to.md).

### Discussion 7: Job Dashboard — Cancel Deferred
- **Context:** The original scope included Cancel, Restart, and Audit for the job dashboard. Cancel for `RUNNING` jobs requires a signal mechanism in `OrchestrationManager`.
- **Critique:** Codebase audit of `BackgroundJobService.executeJobLifecycle` revealed a fundamental problem: the lifecycle method calls `updateJobStatusUni(jobId, COMPLETED, null)` on chain completion regardless of current DB state — any `CANCELLED` status set by a cancel endpoint would be silently overwritten with `COMPLETED`. A real cancel requires: (a) `cancelRequested` flag on `BackgroundJob` + migration, (b) check points in `OrchestrationManager.processPendingAndRetryItemsByPage` (between pages) and `executeTopicProcessingForDate` (between topics), both of which run as reactive Mutiny chains. Estimated ~4–6h backend work — nearly doubling the POV-188 budget. Cancel for `QUEUED`-only has a race condition (QUEUED → RUNNING transition is not atomic from the endpoint's perspective).
- **Decision:** **No cancel in v0.17.0.** Cancel without signal mechanism is not cancel — it is an illusion. Dashboard provides read-only visibility for `RUNNING`/`COMPLETED` jobs and **Restart for `FAILED` jobs only**. Cancel deferred to v0.18.0 with the full signal mechanism. Documented in [improvements.md](../../backlog/improvements.md).

### Discussion 8: POV-189 Scope — Spike Fallback and Quota Tracking
- **Context:** POV-189 has a built-in spike phase to validate the Supadata API. Two scope decisions required: (1) what happens if the spike fails, (2) how deep is quota tracking.
- **Spike fallback decision:** If Supadata API proves unsuitable (wrong format, incompatible contract, unreliable), POV-189 shrinks to **abstraction-only**: `TranscriptProvider` interface + `YouTubeLegacyTranscriptProvider` + jitter. The abstraction itself is never deferred — it is the primary value of the task.
- **Quota tracking decision — A-lite:** Full quota tracking (DB table + API + frontend component) was estimated at ~6.5h. Frontend component was deferred to v0.18.0. v0.17.0 delivers: `transcript_provider_quota_usage` table + `GET /api/v1/admin/transcript/providers` endpoint (backend knows remaining quota for routing decisions). `admin.transcript.*` i18n keys deferred to v0.18.0.

## Phase 2: Technical Hardening & NFRs

### Baseline Audits (2026-05-20)
- **Account Surface:** User entity supports `ENABLED`/`DISABLED` (via Quarkus OIDC integration) but no explicit `PENDING_APPROVAL` state. Login flow auto-creates users with `ENABLED=true` (verified by inspecting OIDC linking flow in v0.10 retrospective).
- **Job Audit:** `JobExecutionAudit` retention is 90 days (POV-165, v0.15.0). No UI surface exists for live job manipulation (cancel/restart) — current "Admin Jobs UI" is a placeholder ([improvements.md](../../backlog/improvements.md)).
- **Transcript Pipeline:** Single-provider (YouTube via `YouTubeTranscriptService`). No retry-with-delay or provider fallback. Anecdotal evidence of transient IP-rate-limit failures during heavy orchestration.

### Performance Budgets
- **Admin User List API:** < 200ms p95 for 1000 users (paginated).
- **Job Dashboard Restart Action:** < 1s round-trip from click to new job visible in list. *(Cancel deferred — see Discussion 7.)*
- **Transcript Provider Fallback:** Total elapsed time with one fallback < 2× single-provider latency budget.
- **External Links Bundle Impact:** < +1 KB gzipped (rehype-external-links).
- **Session Expiry Redirect:** < 300ms from 401 response to login page render.

## Phase 4: Risks & Considerations

| Risk | Mitigation |
|:---|:---|
| **Admin Lockout via Self-Demotion** | Server-side guard: an Admin cannot remove their own `ADMIN_PERMISSION` if they are the last admin. Surface as a form validation error. |
| **Approval Backlog** | Without email, admins may not notice pending users. Mitigation: persistent badge counter on the admin sidebar nav + landing-page widget showing pending count for admins. |
| **Provider Quota Exhaustion (Supadata)** | Free tier is 100/month. Implement quota tracking with degraded fallback to legacy YouTube path. Surface remaining-quota metric on Grafana (best-effort; full alerting in v0.18.0). |
| **Jitter Delay Slows Orchestration** | Adding random delay reduces parallelism. Mitigation: keep jitter bounded (e.g., 0.5–2.5s per video), measure orchestration-duration regression in baseline E2E. |
| **External-Link Plugin Sanitizes Existing Markdown** | `rehype-external-links` operates after `rehype-sanitize`. Verify ordering in each ReactMarkdown call-site to avoid stripping `target`/`rel` attributes downstream. |
| **Session-Redirect Loop** | If `/login` itself returns 401 (misconfigured backend), interceptor would loop. Mitigation: explicit `if (response.url.endsWith('/login'))` short-circuit in interceptor. |
| **Migration Risk (User State)** | Existing users default to `ENABLED` — backfill SQL must NOT mark them PENDING_APPROVAL. Idempotent migration with explicit `WHERE status IS NULL`. |

## Expert Triad Review

### 1. Security & i18n
- **Self-Demotion Guard:** Last-admin protection enforced server-side, not just UI-side.
- **Approval Authorization:** Only users with `USER_APPROVE_PERMISSION` (new PBAC permission) can transition `PENDING_APPROVAL → ENABLED`. Mapped to existing `ADMIN` role.
- **Session-Token Invalidation:** On approval rejection or status `DISABLED`, all active sessions for that user must be terminated (cookie + server-side revoke).
- **i18n:** Tone is formal/professional for admin surfaces (contrast: v0.16.0 onboarding tone was "Osebni asistent"). All admin keys land under the `admin.*` and `account.*` namespaces. Slovenian translations follow technical-administrative register.

### 2. Ops Readiness
- **Rollback (Approval):** **No config flag** — approval is always required per [ADR-0008](../../adr/0008-account-activation-state-machine.md) (a config flag would require maintaining two code paths; test fixtures must be updated to create `ENABLED` users explicitly). Rollback means reverting the migration and code changes. RUNBOOK documents how to seed an initial admin user on fresh deployments.
- **Rollback (Multi-Provider Transcript):** Provider abstraction defaults to `youtube-legacy` if no other provider configured. Supadata integration is opt-in via `transcript.providers.supadata.enabled=false` flag.
- **Panic Switch (External Links):** Plugin can be removed by single revert; no DB state.
- **Job Restart Audit Trail:** Every Restart action writes a `JobExecutionAudit` record on the original job with the acting admin's user ID for forensic traceability. Cancel does not exist in v0.17.0.

### 3. Performance & Bundle
- **Frontend Bundle Impact:** Admin UI screens add ~10-15 KB gzipped (estimated based on v0.16 admin surface additions). Within v0.16.0's 1.1 MB baseline. External-links plugin adds <1 KB.
- **Backend N+1 Audit:** Admin user list endpoint must use `LEFT JOIN FETCH` for roles/permissions, per the v0.16.0 POV-175 pattern. Verified via `QueryCountAssert` utility from v0.16.0.
