# Version 0.11.0 Planning Process

## High-Level Goals
- Establish a comprehensive REST API for a decoupled frontend (API-First).
- Implement fine-grained Security (Permission-Based Access Control - PBAC) targeting specific endpoints.
- Generate and expose OpenAPI/Swagger documentation.
- Implement the Test Data Builder pattern (from v0.10 retrospective).
- Assess and incorporate Automated Dependency Vulnerability Scanning (from Methodology Section 7.1).

## Testing Strategy
- Core entity logic will continue to rely on `@QuarkusTest`.
- We will invest in a **Test Data Builder pattern** to reduce test setup overhead, especially for mocked identities and complex entity relations from the previous version.
- API endpoints will be tested using `RestAssured` focusing on JSON serialization, correct status codes, and authorization rules (`@QuarkusIntegrationTest` and `@TestSecurity`).

## Core Planning Steps

1.  **Frontend Specification (UI/UX & Requirements):** The very first step is to create a detailed `frontend-specification.md`. This document will outline the user flows, necessary screens, and data required for the separate frontend SPA application. This specification must be detailed enough to be handed off to an AI agent for developing the frontend project. It will act as the source of truth for UI/UX expectations.
2.  **API Design & Contract:** Using the `frontend-specification.md`, we will strictly define the REST API surface, including request and response JSON payloads. This ensures the API provides exactly what the frontend needs, thereby mitigating the risk of a "backend-driven" design, as noted in previous retrospectives.
