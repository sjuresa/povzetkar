## 1. Overarching Goal: Standalone Deployment & Technical Stabilization

Version 0.8.0 focuses on preparing the application for production-like environments. The primary deliverable is a containerized application (Docker/Podman) that can run independently. Additionally, we are addressing technical debt accumulated in previous versions (testing patterns, API consistency) to ensure a stable foundation for future features.

## 2. Rationale for Key Decisions

### 2.1. Containerization (Docker/Podman)
We are introducing containerization to decouple the application from the host environment.
**Rationale:**
*   **Deployment:** Essential for consistent deployment across different environments (dev, prod). We aim for OCI compliance to support both Docker and Podman runtimes.
*   **Configuration:** Forces us to externalize all configuration (DB URLs, API keys) via environment variables.

### 2.2. Testing Guide & BOM Alignment
We are prioritizing the creation of a Testing Guide and cleaning up `pom.xml`.
**Rationale:**
*   **Process Debt:** The v0.7.0 retrospective highlighted significant friction due to incorrect testing patterns and dependency conflicts. Fixing this now prevents future waste.
*   **Stability:** Relying on the Quarkus BOM ensures we use compatible library versions.

### 2.3. Refactoring Orchestration API
We are refactoring the orchestration endpoint to use a Request Object and standardizing the frontend AJAX calls.
**Rationale:**
*   **Maintainability:** The current method signature is unwieldy. A Request Object (`OrchestrationRequest`) allows for easier extension without breaking signatures.
*   **Consistency:** Moving from Query Parameters to a JSON Body is standard for `POST` requests and simplifies the frontend logic.

### 2.4. Standardized Logging
We are implementing a standard logging format for entity processing.
**Rationale:**
*   **Observability:** In a containerized environment, logs are the primary window into the application. Consistent logs (with IDs, durations, Topics, Authors) are crucial for debugging and filtering.

## 3. Testing Strategy

*   **Container Testing:** We will verify the container image builds and runs locally, connecting to a local database.
*   **API Testing:** The refactored Orchestration API will be tested with integration tests ensuring the JSON body is correctly parsed and validated.
*   **Regression:** We will ensure existing functionality (Orchestration, Admin UI) remains intact after the refactoring.

## 4. Deferred Items

*   **Advanced Rate Limiting:** Deferred to v0.9 (Production Hardening).
*   **Time Period Briefings:** Deferred to v0.9.
