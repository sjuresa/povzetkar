## 1. Overarching Goal: Foundational UI/UX with Minimal Investment

The primary goal of version 0.6.1 is to significantly improve the usability and visual appeal of the existing server-side rendered UI. The core strategy is to achieve maximum impact with minimal, non-locking investment. This means we will avoid committing to a heavy frontend framework (like Angular or React) at this stage, keeping future architectural options open.

The plan, as outlined in `roadmap.md`, focuses on establishing a clean, responsive, and navigable baseline experience.

## 2. Rationale for Key Decisions

### 2.1. Adopting a "Class-less" CSS Framework

Instead of a comprehensive framework like Bootstrap, which requires significant changes to HTML (adding specific classes), we will integrate a "class-less" framework like **Pico.css**.

**Rationale:**
*   **High ROI:** Provides an immediate, modern look and feel by styling standard HTML elements directly.
*   **Minimal Intrusion:** Requires almost no changes to the existing HTML structure, making integration fast and simple.
*   **Non-Locking:** Since we are not littering the HTML with framework-specific classes, swapping it for another framework (or a full SPA) in the future will be trivial.

### 2.2. Structuring Tasks for Incremental Improvement

The tasks in `v0.6.1-tasks.md` are structured to build upon each other logically:
1.  **Task 1 (Layout & Styling):** Establishes the visual and structural foundation by creating a master layout and integrating the Pico.css framework for a consistent, modern look.
2.  **Task 2 (Navigation & Feedback):** Improves user orientation and interaction by implementing dynamic breadcrumbs and a system-wide "flash message" mechanism.
3.  **Task 3 (Refactoring & Usability):** Addresses code quality and critical usability issues by refactoring to semantic HTML, improving form handling, and replacing the non-scalable content source dropdown with a searchable page.
4.  **Task 4 (Admin Actions):** Enhances manageability by creating a dedicated UI for triggering core system processes like content enrichment and orchestration.
5.  **Task 5 (Verification & Review):** Serves as the final quality gate, ensuring all changes work together through a combination of automated backend tests and a structured manual test plan covering all new features and responsiveness.

### 2.3. Adapting the Plan: Handling Unplanned Discoveries

While the initial task list in `v0.6.1-tasks.md` provides a clear structure, we recognize that not all issues can be foreseen. We follow a pragmatic process for handling unplanned discoveries, as formalized in `docs/sdlc/11_development_checklist.md` (point 2.9).

Prime examples during this version's planning included:
*   **The non-scalable `ContentSource` dropdown:** Identified as a critical usability blocker and addressed by replacing it with a searchable page (Task 3).
*   **The need for UI-driven admin actions:** Addressed by creating a new Admin page (Task 4) to improve manageability.

Consequently, we adapted the plan by creating **Task 4** and updating **Task 3** in `v0.6.1-tasks.md` to include these crucial improvements, demonstrating our ability to remain agile while staying focused on the overarching goal.

### 2.4. Rationale for the Testing Strategy

For this version, we are consciously deferring the implementation of a full end-to-end (E2E) UI testing framework (like Playwright). This decision aligns with our "minimal, non-locking investment" goal, as the UI's long-term architecture is not yet finalized.

Instead, we are adopting a two-pronged, pragmatic approach:
1.  **Backend Integration Tests:** We will extend existing `@QuarkusTest` classes to verify that our UI endpoints return the correct HTML structure and data. This provides automated checks for the data layer of the UI.
2.  **Formalized Manual Testing:** We have created a detailed, structured manual test plan within `Task 5`. This ensures that all user flows, interactions, and responsiveness are verified consistently before the version is considered complete.

## 3. Process Improvement: Adopting a "Definition of Done" (DoD)

As proposed in `docs/sdlc/07_development_methodology_comparison.md` and inspired by the v0.6 retrospective, we are formally adopting a **Definition of Done (DoD)** for this version onwards. This is a crucial step to ensure consistency, quality, and clarity on when a task is truly complete.

### 3.1. The "Definition of Done" for v0.6.1

A task will be considered "Done" only when all the following criteria are met:

1.  **Functionality Implemented:** The code delivers the functionality described in the task's acceptance criteria.
2.  **Tests Passing:** All existing and new unit/integration tests pass successfully.
3.  **Documentation Updated:** The `## Documentation` section of the task is fully addressed:
    *   All documents listed under `Update:` have been modified as required.
4.  **UI is Responsive:** The changes are verified to be functional and readable on both desktop and mobile viewports.
5.  **Commit Message Approved:** The final commit message is reviewed and adheres to the Conventional Commits standard.
6.  **Code Quality Maintained:** The code is clean, readable, and adheres to project-level coding standards and architectural principles.

### 3.2. Integration into Workflow

This DoD will be explicitly referenced during the "Task Execution" phase of our development process. It will serve as the final checklist before a task is committed and marked as complete. This formalizes quality control and ensures no aspect (like documentation updates or responsiveness checks) is overlooked.

## 4. Preliminary Notes for Retrospective

*This section captures key learnings and observations from the planning phase to serve as input for the official end-of-version retrospective.*

1.  **The Importance of Early Test Strategy Definition:** The question "How will we test this?" emerged late in the planning process but proved crucial. It led to a pragmatic, proportional testing strategy. For future versions, this question must be addressed at the very beginning of planning, as now formalized in `docs/sdlc/11_development_checklist.md`.

2.  **Iterative Planning as a Strength:** The initial plan was significantly improved through iterative discussion (e.g., adding the scalable content source selection, the Admin page). This confirms that our planning phase should be treated as a dynamic dialogue rather than a static, one-off task.

3.  **Active Management of Technical Debt:** Instead of just logging the non-scalable dropdown, we assessed its criticality and integrated the solution into the current version's plan. This proactive approach to managing critical usability issues should be maintained.
