# Version 0.17.0 Planning Process: Administrative Control & User Onboarding

**Status:** Concluded
**Date:** 2026-05-24

## Introduction

This document captures the planning decisions for v0.17.0. The version goal — **Administrative Control & User Onboarding** — was established in the roadmap update (rev 3.6, 2026-05-20) after deferring Hardening (DAST, Grafana alerts, full-text search) to v0.18.0 to preserve execution quality.

---

## Phase 1: Strategic Evaluation & Scope Definition

### Discussion 1: Scope Compression — Hardening vs. Governance

- **Initial Roadmap Proposal:** v0.17.0 to include both Admin Center and Hardening (DAST, Grafana alerting, full-text search).
- **Decision:** Compressed scope to Admin Center + UX fixes only. Hardening moved entirely to v0.18.0.
- **Justification:** Hardening tasks are independent of user-facing governance; deferring them avoids context-switching and ensures the activation state machine and job dashboard receive full attention.

### Discussion 2: Email Deferral (User Approval Notifications)

- **Initial Proposal:** SMTP-driven admin notification on new pending user; user notification on approve/reject.
- **Decision:** Deferred. No SMTP infrastructure exists in the project. Approval discovery falls back to admin sidebar badge.
- **Impact:** Logged in [ADR-0008](../adr/0008-account-activation-state-machine.md) and `improvements.md`.

### Discussion 3: Cancel Deferral (POV-188)

- **Initial Proposal:** Job cancel in scope for POV-188.
- **Decision:** Deferred after codebase audit revealed `executeJobLifecycle` overwrites any `CANCELLED` status with `COMPLETED` on finish — making cancel without a signal mechanism an illusion.
- **Design documented:** `improvements.md` — "Background Job Cancel (Signal Mechanism)".

## Phase 2: Architecture Decisions

### ADR-0008 — Account Activation State Machine

- **Decision:** Four-state enum (`PENDING_APPROVAL`, `ENABLED`, `DISABLED`, `REJECTED`); no config flag bypass.
- **Key constraint:** ADR-0008 explicitly rejects a `account.approval.required=false` feature flag — all new sign-ins land in `PENDING_APPROVAL`.
- **Ref:** [docs/adr/0008-account-activation-state-machine.md](../adr/0008-account-activation-state-machine.md)

### ADR-0009 — Multi-Provider Transcript Strategy

- **Decision:** `TranscriptProvider` interface + `TranscriptOrchestrator` ordered fallback chain. Supadata as pilot second provider (opt-in default: disabled).
- **Spike finding:** Supadata requires full YouTube URL, not `videoId` — discovered during live API test, preventing a mis-implementation.
- **Ref:** [docs/adr/0009-multi-provider-transcript-strategy.md](../adr/0009-multi-provider-transcript-strategy.md)

### ADR-0010 — Session Expiry Handling

- **Decision:** 401 interceptor → `/auth/login?redirect=<path>`; `LoginResource.resolveSafeDestination()` handles return. `sessionStorage` not used.
- **Insight:** Discovered during planning interview by reading `LoginResource.java` — the `?redirect=` param already existed and was safe to use.
- **Ref:** [docs/adr/0010-session-expiry-handling.md](../adr/0010-session-expiry-return-to.md)

## Phase 3: Process Improvement Applied This Cycle

### PPP §2.5 — Pre-Interview Codebase Audit (added 2026-05-21)

The initial planning session (2026-05-20) produced task definitions based on assumed codebase state rather than observed state, resulting in 5 factual errors corrected in a second session (2026-05-21) and approximately 2h of rework. The fix — mandating source-file reading before any planning artifact is written — was formalized as PPP §2.5.

**Impact:** All subsequent tasks (POV-185 through POV-189) were planned with deliberate codebase reads in the interview phase. Zero mid-execution reversals in those tasks.
