### **Task 1 POV-74: Implement Orchestration Robustness**

**Title:** `feat(orchestration): add retry logic and overlapping run handling`

**Description:**
Enhance the `OrchestratorService` to be more resilient to transient failures. This involves two key improvements: re-processing items that previously failed with a recoverable error, and ensuring the orchestration lock is respected under all conditions.

**Acceptance Criteria:**
- **Retry Logic:**
    - **Test:** A test is written to verify that `ContentItem`s with status `RETRY_LATER` are picked up for processing at the start of a new orchestration run.
    - **Implementation:** The `OrchestratorService` is modified to query for and process items with `RETRY_LATER` status.
- **Locking Mechanism:**
    - **Test:** A test is written to simulate a scenario where an orchestration run is triggered while another is already in progress (or has exceeded the lock time).
    - **Implementation/Analysis:** The `OrchestrationLock` mechanism is reviewed. If a flaw is found, it is fixed. The analysis should consider what happens if an orchestration takes longer than the lock's configurable timeout (defaulting to 10 minutes).

### **Task 2 POV-75: Improve Briefing Generation Flexibility**

**Title:** `feat(briefing): decouple briefing generation and add retry logic`

**Description:**
Make the briefing generation process more flexible and robust. Decouple it from the main orchestration flow to allow generation even when no new content is fetched. Add retry logic for transient failures during generation.

**Acceptance Criteria:**
- **Transient Failure Handling:**
    - **Test:** A test is written to simulate a transient failure (e.g., a 503 error from the GenAI service) during meta-summary generation.
    - **Implementation:**
        - A new status field (e.g., `GENERATION_STATUS` with values `PENDING`, `COMPLETED`, `FAILED_TRANSIENT`) is added to the `Briefing` entity.
        - The `BriefingService` is updated to catch transient errors and set the status to `FAILED_TRANSIENT`.
        - The `OrchestratorService` is updated to re-trigger generation for briefings with this status.
- **Generation from Existing Content:**
    - **Test:** A test is written for the following scenario: a new `Topic` is created, and content sources are added that contain `ContentItem`s already summarized in the database.
    - **Implementation:** The `OrchestratorService` or a new dedicated service is modified to detect this scenario and trigger briefing generation for the new topic using existing summaries.

### **Task 3 POV-76: [Spike] Analyze GenAiPool Concurrency Behavior**

**Title:** `test(ai): spike - analyze GenAiPool concurrency behavior`

**Description:**
This is a research task (Spike) to understand how `GenAiPool` behaves under concurrent load. The test created for this task is a tool for analysis; it can be disabled (`@Disabled`) after the spike is complete. The primary deliverable is the **knowledge** formalized in a new analysis document.

**Acceptance Criteria:**
- A new, dedicated `@QuarkusTest` class is created for this analysis.
- The test simulates at least 3 concurrent threads attempting to acquire a client from a pool of 2.
- The test verifies and documents the behavior: Do subsequent threads block and wait, or do they fail?
- **Deliverable:** The findings and code from the test are documented in a new `docs/analysis/GenAiPool_Concurrency_Analysis.md` file, with a clear recommendation on whether further action is needed.

### **Task 4 POV-77: Implement Base UI Test Class**

**Title:** `refactor(test): create BaseUITest to standardize UI test setup`

**Description:**
Address the "fragile test suite" issue identified in the v0.6.1 retrospective. Create a common base class for all UI-related integration tests to encapsulate and standardize database cleanup and common setup logic, preventing state pollution between tests.

**Acceptance Criteria:**
- **Test (Reproduce Failure):** The existing UI tests are run as a suite to confirm the "state pollution" issue can be reproduced.
- **Implementation:**
    - A new abstract class `BaseUITest` is created in the `src/test/java` tree.
    - This class contains `@BeforeEach` and `@AfterEach` methods that handle transactional database cleanup (e.g., deleting all records from relevant tables).
    - At least two existing UI test classes (e.g., `AdminResourceTest`, `TopicResourceTest`) are refactored to extend `BaseUITest` and remove their local cleanup logic.
- **Verification:** The entire test suite is run again to confirm that all tests now pass reliably as a suite.

### **Task 5 POV-78: Implement Briefing Generation for a Time Period**

**Title:** `feat(briefing): allow briefing generation for a date range`

**Description:**
Add the functionality to generate a single briefing that covers a user-specified time period (e.g., a week, a month) for a given topic, instead of just a single day.

**Acceptance Criteria:**
- **Backend Logic:**
    - **Test:** A test is written for the `BriefingService` that calls a new method, `generateBriefingForPeriod(Topic topic, LocalDate start, LocalDate end)`.
    - **Implementation:**
        - A new method `generateBriefingForPeriod` is added to `BriefingService`.
        - This method queries for all `Summary` entities for the given topic within the date range.
        - It generates a single `Briefing` entity that aggregates all these summaries.
        - The title of the briefing should reflect the date range (e.g., "Briefing for AI: 2025-11-01 to 2025-11-07").
- **Frontend UI:**
    - **Test:** A new UI test is added to verify a new form on the topic detail page.
    - **Implementation:**
        - The `topic-detail.html` template is updated with a new form containing `startDate` and `endDate` inputs and a "Generate Weekly Briefing" button.
        - The `TopicResource` is updated with a new endpoint to handle this form submission, call the new service method, and redirect back with a success message.

### **Task 6 POV-79: Implement Rate Limiting for Transcription API**

**Title:** `feat(transcription): implement rate limiting for API calls`

**Description:**
Implement a rate-limiting mechanism to prevent exceeding the quota of the external transcription API. This will ensure system stability and avoid service interruptions due to excessive requests.

**Acceptance Criteria:**
- **Test:** A test is written that attempts to call a mocked transcription service multiple times in rapid succession.
- **Implementation:**
    - A rate-limiting component is implemented (e.g., using a Guava RateLimiter or a simple time-based check in a dedicated service).
    - The service responsible for calling the transcription API is modified to use this rate limiter before making an external call.
- **Verification:** The test is updated to verify that the rate limiter correctly spaces out the calls to the mocked service, ensuring that no more than N requests are made per second.
