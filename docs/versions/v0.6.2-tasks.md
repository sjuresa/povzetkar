### **Task 1 POV-74: Implement Orchestration Robustness (Completed)**

**Title:** `feat(orchestration): add retry logic and overlapping run handling`

**Description:**
Enhance the `OrchestratorService` to be more resilient to transient failures. This involves two key improvements: re-processing items that previously failed with a recoverable error, and ensuring the orchestration lock is respected under all conditions.

**Acceptance Criteria:**
- **Retry Logic:**
    - **Test:** A test is written to verify that `ContentItem`s with status `RETRY_LATER` are picked up for processing at the start of a new orchestration run.
    - **Implementation:** The `OrchestratorService` is modified to query for and process items with `RETRY_LATER` status.
- **Locking Mechanism:**
    - **Test:** A test is written to simulate a scenario where an orchestration run is triggered while another is already in progress (or has exceeded the lock time).
    - **Implementation/Analysis:** The `OrchestrationLock` mechanism is reviewed. If a flaw is found, it is fixed. The analysis should consider what happens if an orchestration takes longer than the lock's configurable timeout (defaulting to 10 minutes).

### **Task 2 POV-75: Improve Briefing Generation Flexibility (Completed)**

**Title:** `feat(briefing): decouple briefing generation and add retry logic`

**Description:**
Implement a robust, idempotent briefing generation process. The system should automatically create or regenerate a briefing for a given day if it doesn't exist or if it doesn't include all available content summaries for that day. This removes the need for a separate status field on the `Briefing` entity.

**Acceptance Criteria:**
- **Test:** A test is written for the following scenario: a `Briefing` for a specific day does not exist, but there are `ContentItem`s with completed summaries for that day. The test verifies that a new `Briefing` is created.
- **Test:** A test is written for a scenario where a `Briefing` already exists, but a new `ContentItem` with a completed summary is added for the same day. The test verifies that the existing `Briefing` is deleted and a new one is generated that includes all summaries.
- **Implementation:** The `OrchestratorService` is modified to implement this idempotent logic: for each day, it compares the set of summaries included in the existing briefing with the set of all available summaries. If they don't match, the old briefing is overwritten.

### **Task 3 POV-76: [Spike] Analyze GenAiPool Concurrency Behavior (Completed)**

**Title:** `test(ai): spike - analyze GenAiPool concurrency behavior`

**Description:**
This is a research task (Spike) to stress-test the `GenAiPool` under high concurrent load. The goal is to verify the correctness of the cooldown logic, analyze the impact of blocking calls (`Sleeper.sleep`), and understand its overall behavior. The test created for this task is a tool for analysis; it can be disabled (`@Disabled`) after the spike is complete. The primary deliverable is the **knowledge** formalized in a new analysis document.

**Acceptance Criteria:**
- A new, dedicated `@QuarkusTest` class is created for this analysis.
- The test simulates a high number of concurrent threads (e.g., 20) attempting to acquire a client from a small pool (e.g., 2).
- The test must verify and document the behavior of the `GenAiPool`:
    - Do subsequent threads block and wait for a client, or do they fail?
    - **Cooldown Verification:** The test must specifically verify that after a client (and its API key) is used, it is not used again until the `cooldown.period.sec` has passed, even under high concurrent load.
    - **`Sleeper.sleep` Analysis:** The test should analyze the impact of `Sleeper.sleep`. If it is found to be a blocking operation that holds up worker threads, the analysis should propose a non-blocking alternative (e.g., using `Uni.createFrom().emitter()` with a delay).
- **Deliverable:** The findings, code prototypes, and analysis are documented in a new `docs/analysis/GenAiPool_Concurrency_Analysis.md` file. The document must include clear recommendations on:
    - Whether the current concurrency model is safe.
    - Whether the cooldown period is correctly enforced.
    - A recommended non-blocking approach if `Sleeper.sleep` is problematic.

### **Task 4 POV-77: Implement Just-in-Time Scheduling for GenAI Tasks (Completed)**

**Title:** `feat(orchestration): implement just-in-time scheduling for GenAI tasks`

**Description:**
Refactor the orchestration of content summarization to prevent thread exhaustion. **Do not modify `GenAiPool`** (if it is not necessary). Instead, implement a "just-in-time" scheduling mechanism where the processing of the *next* content item is triggered only after the *current* item has successfully acquired a `GenAiClient`.
This ensures that we do not spawn threads that simply sit and block waiting for the rate limit (cooldown). A new thread is created/submitted only when a client becomes available for the previous task.
**Important:** Do not simply limit the thread pool size to the number of API keys. Since content generation can take longer than the cooldown period, it is valid and expected to have more active threads than API keys. The goal is to limit the threads *waiting* for a key, not the threads *using* a key.

**Acceptance Criteria:**
- **Scheduling Logic:**
    - **Implementation:** Modify `OrchestratorManager` to implement a chained execution flow.
    - **Implementation:** The flow must be:
        1. Task N calls `GenAiPool.getGenAiClient()` (blocking).
        2. Upon return (client acquired), Task N immediately triggers the submission of Task N+1 to the executor.
        3. Task N proceeds to call `generateContent`.
- **Verification:**
    - **Test:** A test simulates a scenario with 2 API keys (short cooldown) and multiple content items.
    - **Test:** Verify that the number of active/blocked threads does not explode. Specifically, ensure that a new task is not started until the previous one has passed the rate-limit check.

### **Task 5 POV-78: Implement Base UI Test Class (Failed)**

**Title:** `refactor(test): create BaseUITest to standardize UI test setup`

**Description:**
Address the "fragile test suite" issue identified in the v0.6.1 retrospective. Create a common base class for all UI-related integration tests to encapsulate and standardize database cleanup and common setup logic, preventing state pollution between tests.

**Acceptance Criteria:**
- **Test (Reproduce Failure):** The existing UI tests are run as a suite to confirm the "state pollution" issue can be reproduced.
- **Implementation:**
    - A new abstract class `BaseUITest` is created in the `src/test/java` tree.

    - At least two existing UI test classes (e.g., `AdminResourceTest`, `TopicResourceTest`) are refactored to extend `BaseUITest` and remove their local cleanup logic.
- **Verification:** The entire test suite is run again to confirm that all tests now pass reliably as a suite.
