# v0.10.0 Planning Process: User Management & Security

**Status:** In Progress
**Date:** 2026-02-13

## 1. Review of Previous Retrospective
*Action:* Reviewed learnings from v0.9.0.
*Key Takeaway:* Strict adherence to "Usage Analysis" and "Client-Side Analysis" mandates is required to prevent regressions. We must also ensure no blocking calls exist in the new security filters.

## 2. High-Level Goals
The primary focus of v0.10.0 is **User Management & Security**. This is a critical infrastructure layer that transforms the application from a single-user tool into a multi-tenant platform.

Additionally, we are addressing "Developer Experience & Observability" by improving documentation, API visibility (Swagger), and auditing (ModifiedAt).

### Primary Objectives
1.  **User Management (The Core):** Implement Authentication (Who are you?) and Authorization (What can you do?).
2.  **Multi-tenancy:** Ensure users only see their own Topics and Content Sources.
3.  **Developer Experience:** Standardize project structure documentation, API documentation, and testing patterns.
4.  **Operational Logic:** Filter content based on duration (min video length).
5.  **UI Enhancements:** Expose Changelog and Roadmap within the application.

## 3. Testing Strategy
Given the security-critical nature of this release, the testing strategy shifts slightly:
*   **Security Testing:** We must write specific integration tests (`@QuarkusTest`) that verify *access denial* for unauthenticated users and *data isolation* between different users (Tenant A cannot see Tenant B's data).
*   **Unit Testing:** The new filtering logic (Min Video Length) will be tested with pure Unit Tests.
*   **Integration Testing:** We will align our testing practices with `mastering-testing.md`, ensuring a clear distinction between `@QuarkusTest` (component/mocked) and `@QuarkusIntegrationTest` (black-box).

## 4. Architectural Decisions (ADRs)
Starting with v0.10.0, we are adopting **Architectural Decision Records (ADRs)**.
*   **ADR-001:** Record Architecture Decisions (Meta-decision).
*   **ADR-002:** Authentication Mechanism (Form-based vs. OIDC/JWT). This will be the first major decision to document during POV-106.

## 5. Task Breakdown Strategy
The "User Management" feature is too large for a single task. It has been broken down into:
*   **Data Model:** Entities and Database Schema.
*   **Infrastructure:** Security setup and Auth mechanism.
*   **Multi-tenancy:** Refactoring existing queries to be user-aware.
*   **UI:** Frontend integration.

## 6. Risk Assessment
*   **Security Gaps:** Implementing custom auth always carries risks. We will mitigate this by using standard Quarkus Security extensions and avoiding custom crypto.
*   **Data Migration:** Adding `user_id` to existing tables requires careful migration strategies (e.g., assigning existing data to a default admin user).
*   **Performance:** Adding RLS (Row Level Security) logic or `WHERE user_id = ?` clauses to every query might impact index usage. We will monitor query performance.

## 7. Definition of Done (DoD) for v0.10.0

*   [ ] `mvn clean verify` passes.
*   [ ] Users can log in and log out.

*   [ ] API documentation (Swagger) is available.
*   [ ] Changelog and Roadmap are visible in the UI.
*   [ ] ADR-001 and ADR-002 are created.
