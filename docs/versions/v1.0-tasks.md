This document lists the concrete tasks for version 1.0. The primary goal of this version is to introduce support for multiple topics or categories (e.g., AI, Programming, Politics). Each topic will have its own configurable list of channels and a dedicated output Git repository.

This feature builds upon the fully migrated and stable Quarkus application architecture established in version 0.9.

### **Task 1 [POV-60]: Extend Data Model for Topic-Specific Configuration**

**Title:** `feat(model): Extend Topic entity with output repository path`

**Description:**
This task extends the database schema to support topic-specific output repositories. This is a prerequisite for the core feature of this version.

**Acceptance Criteria:**
- The `Topic` JPA entity is updated to include a new field, e.g., `outputRepositoryPath` (String).
- Database migration scripts (e.g., Flyway or Liquibase) are updated to reflect the new schema.

---

### **Task 2 [POV-61]: Implement Topic Configuration Enrichment**

**Title:** `feat(config): Enrich Topic entities from application.properties on startup`

**Description:**
This task creates a mechanism to configure topic-specific properties from `application.properties`. Instead of populating data, this service will **enrich** the `Topic` entities that already exist in the database (migrated in v0.5) with their corresponding output repository paths.

**Acceptance Criteria:**
- The application can parse a list of topic configurations from `application.properties` (e.g., `povzetkar.topics.ai.repo.path=/path/to/ai-repo`).
- A startup service (`@ApplicationScoped`) is created that:
  1. Fetches all `Topic` entities from the database.
  2. For each topic, finds its corresponding configuration in `application.properties`.
  3. Updates the `outputRepositoryPath` field on the entity.
  4. Persists the changes back to the database.
- The service logs a warning if a `Topic` entity exists in the database but has no corresponding configuration in the properties file.

---

### **Task 3 [POV-62]: Refactor Core Workflow to be Topic-Aware**

**Title:** `refactor(core): Refactor the main workflow to process topics sequentially`

**Description:**
This is the main task to refactor the application's orchestrator. The main loop will now iterate over all configured topics from the database. For each topic, it will execute a parameterized summarization and publishing workflow.

**Acceptance Criteria:**
- The main application orchestrator (the Quarkus `@Scheduled` job) fetches all active `Topic` entities from the database.
- The application iterates through each `Topic` one by one.
- For each topic, the workflow (fetching, summarization, documentation generation, Git push) is executed using only the channels and the output repository path associated with that specific topic.
- Services like `ReportingService` and the Git integration logic are refactored to accept the output path as a parameter, removing any hardcoded paths.
- The application correctly generates summaries and pushes them to the appropriate, separate Git repositories for each topic.
