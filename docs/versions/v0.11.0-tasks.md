# Version 0.11.0 Tasks: API-First & Advanced Security

## Goals
- Design and implement REST API for all core resources.
- Implement PBAC (Permission-Based Access Control).
- Document the API via OpenAPI/Swagger.
- Address technical debt regarding test data setup and integrate dependency vulnerability scanning.

## Task Breakdown

### Task 1 POV-114: (Completed) [Spec] Frontend Specification (UI/UX & Requirements)
- **Description:** Create a comprehensive frontend specification document. This is a prerequisite for the API design. It must detail:
  1. The required screens and user flows.
  2. The data needed for each view.
  3. **Role/Permission (PBAC) implications:** Which UI elements (buttons, pages, actions) are visible or enabled based on the user's roles or permissions.
  This specification should be detailed enough to be handed off to an AI agent (or team) for the development of a separate frontend application project.
- **Documentation:**
  - `Context`: We need to understand the client's needs before exposing the API.
  - `Update`: Create a new `docs/analysis/frontend-specification.md` document.

### Task 2 POV-115: (Completed) [Design] API Contract & Data Structures
- **Description:** Based entirely on the `frontend-specification.md` from Task 1, design the exact REST API payload requirements. Outline the JSON data structures for topics, briefings, summaries, and user profiles. This ensures a frontend-driven API design, preventing over-fetching or under-fetching.
- **Documentation:**
  - `Context`: Translating UI requirements into a backend contract.
  - `Update`: Create a new `docs/analysis/api-design.md` document or provide an initial OpenAPI YAML draft.

### Task 3 POV-116: (Completed) Implement Test Data Builder Pattern
- **Description:** Implement builder classes for core entities (`User`, `Topic`, `ContentSource`, etc.) to streamline test data generation and resolve testing pain points originating from v0.10.
- **Documentation:**
  - `Context`: Setting up entities with mandatory fields has become cumbersome in tests.
  - `Update`: Mention the new pattern in `docs/process/mastering-testing.md`.

### Task 4 POV-117: (Completed) Core API Implementation (Topics & Sources)
- **Description:** Implement the REST endpoints for Topics (`/api/v1/topics`) and Content Sources (`/api/v1/sources`). Strictly follow the Backend-For-Frontend (BFF) pattern using DTO mappers (e.g., MapStruct) to prevent exposing JPA entities. **Security is a prerequisite:** Endpoints must be explicitly secured with full PBAC annotations, as the core PBAC model (Task 5) will be built and merged concurrently.
- **Sub-task (test):** Add comprehensive `RestAssured` tests for the new endpoints, validating structure, pagination, and both success (e.g., 200, 201, 204) and failure status codes (including `401 Unauthorized` and `403 Forbidden`).
- **Documentation:**
  - `Context`: The implementation must strictly fulfill the contract defined in `docs/analysis/api-design.md` to support the SPA transition.
  - `Update`: Keep inline OpenAPI annotations up-to-date in code to perfectly reflect `api-design.md`.
- **Definition of Done:**
  - [ ] CRUD endpoints for Topics and Sources exist and return the exact DTO JSON structures.
  - [ ] The `POST /api/v1/topics/{id}/trigger-run` action endpoint is implemented.
  - [ ] List endpoints implement 0-indexed pagination with `items` and `totalCount`.
  - [ ] Responses construct `sourceUrl` from an identifier dynamic field.
  - [ ] **Security:** Endpoints explicitly secured with appropriate PBAC annotations. `@TestSecurity` integration tests verify authorized and unauthorized (401/403) access.
  - [ ] `RestAssured` tests cover all success and failure paths.

### Task 5 POV-118: (Completed) Implement PBAC (Roles & Permissions)
- **Description:** Execute Step 2 of ADR-003. Define the granular permissions listed in the API contract (e.g., `TOPIC_CREATE`, `SOURCE_VIEW`, `USER_MGMT_UPDATE`) and the mechanism to map these to user roles within the system. This establishes the foundation for the remaining API implementations.
- **Sub-task (test):** Unit test the permission mapping and evaluation logic.
- **Documentation:**
  - `Context`: The application needs fine-grained access control to isolate tenant data rigorously, enforcing the exact matrix from `docs/analysis/frontend-specification.md` and `docs/analysis/api-design.md`.
  - `Update`: Document the permissions model in `docs/analysis/04_database_design.md` or a dedicated security analysis document.
- **Definition of Done:**
  - [ ] `Permission` enum or constants created reflecting all rights in `api-design.md`.
  - [ ] Logic implemented to resolve effective permissions from a user's roles.
  - [ ] Unit tests written for permission generation.

### Task 9 POV-122: Core API Refactoring (CQRS, ContentItems, Ownership)
- **Description:** Refactor the existing API implementation to align with the revised `api-design.md`. This includes replacing `PUT` with `PATCH`, renaming command paths to follow CQRS (`/commands/trigger-run`), and introducing `ContentItem` as a first-class resource (`/api/v1/content-items`). Enforce and test instance-level ownership authorization logic.
- **Sub-task (test):** Update existing `RestAssured` tests and add specific `@TestSecurity` tests verifying authorized access and confirming `403 Forbidden` for other users' resources.
- **Documentation:**
  - `Context`: Ensuring the core API aligns with the strict v0.11 specs before exposing endpoints to the frontend.
- **Definition of Done:**
  - [ ] All `PUT` endpoints replaced with `PATCH`.
  - [ ] Action endpoints refactored to standard `/commands/*` paths.
  - [ ] First-class `ContentItems` endpoints (`GET /api/v1/content-items`, `GET /api/v1/content-items/{id}`) and explicit command endpoints (`retry`, `generate-summary`) are implemented.
  - [ ] Root-level command endpoint `POST /api/v1/briefings` is implemented.
  - [ ] View job item (`GET /admin/jobs/{jobId}`) endpoint is implemented.
  - [ ] **Security:** Instance-level ownership is enforced and verified with tests.

### Task 12 POV-125: Automated Security Scanning (Dependencies & SAST)
- **Description:** Implement a robust automated security scanning process in the CI/CD pipeline or define a local process. This includes:
  1. **Dependency Vulnerability Scanning:** Checking for known vulnerabilities in third-party libraries (e.g., OWASP dependency-check, Trivy).
  2. **Static Application Security Testing (SAST) / Code Quality:** Checking the source code itself for security flaws, bad practices, and potential bugs (e.g., integrating SonarQube, SpotBugs, or a similar tool).
- **Documentation:**
  - `Context`: Ensuring both our code and our dependencies meet security standards as part of the "Advanced Security" theme for v0.11.
  - `Update`: Add the chosen tools and processes to `11_development_checklist.md` as mandatory steps.
- **Definition of Done:**
  - [ ] A dependency scanning tool (e.g., OWASP dependency-check, Trivy) is integrated into the CI pipeline.
  - [ ] The CI build fails if a new vulnerability above a defined severity threshold (e.g., HIGH) is detected.
