### **Task 1 [POV-29]: Optimize YouTube API Quota Usage**

**Title:** `refactor(youtube): Consolidate API calls to reduce quota usage`

**Description:**
This task refactors `YouTubeDataService` to combine two separate API calls for author details and uploads playlist ID into a single call. This halves the API quota cost for fetching author information, making the application more efficient and resilient to quota limits.

**Acceptance Criteria:**
- The `Author` record is updated to include the `uploadsPlaylistId`.
- `YouTubeDataService.getAuthorDetails` is updated to fetch `snippet`, `statistics`, and `contentDetails` in one request.
- The redundant `YouTubeDataService.getUploadsPlaylistId` method is removed.
- `VideoSummarizationService` is updated to use the new `author.uploadsPlaylistId()` method instead of calling the removed method.
- All existing tests related to author details and video fetching pass successfully.

### **Task 2 [POV-30]: Refactor and Simplify Video Fetching Logic**

**Title:** `refactor(youtube): Simplify video fetching and pagination logic`

**Description:**
This task refactors the `fetchPlaylistItems` method in `YouTubeDataService` to improve clarity and maintainability. The complex pagination logic, which relies on helper records and fragmented methods, is replaced by a more linear, self-contained loop.

**Acceptance Criteria:**
- The `fetchPlaylistItems` method is refactored to handle all filtering and stopping conditions within a single `do-while` loop.
- The private helper records `PageProcessingResult` and `ItemProcessingStatus` are removed.
- The helper methods `processPage`, `getItemProcessingStatus`, `shouldStopFetching`, and `addUpToMax` are removed or their logic is inlined into the main loop.
- The application's video fetching behavior remains identical to the previous implementation, and all relevant tests pass.

### **Task 3 [POV-31]: Relocate YouTubeDataService to Service Package**

**Title:** `refactor(structure): Move YouTubeDataService to the service package`

**Description:**
This task relocates the `YouTubeDataService` class from the `ai` package to the `service` package. This move improves architectural consistency by grouping all data-providing services together and clarifying the role of the `ai` package.

**Acceptance Criteria:**
- The file `YouTubeDataService.java` is moved from `src/main/java/si/jumis/ai` to `src/main/java/si/jumis/service`.
- The package declaration in the file is updated to `package si.jumis.service;`.
- All import statements across the project that reference `YouTubeDataService` are updated to the new package.
- The application compiles and all tests pass without any regressions.

### **Task 4 [POV-32]: Decouple ResourceReader for Better Testability**

**Title:** `refactor(service): Decouple ResourceReader for better testability`

**Description:**
This task refactors `VideoSummarizationService` to receive its `ResourceReader` dependency via the constructor instead of creating it internally. This change adheres to the Dependency Inversion Principle, decouples the service from a concrete implementation, and significantly improves its unit testability by allowing mock readers to be injected during tests. While `ResourceReader` may be deprecated in the future Quarkus version, this change improves the quality and testability of the current codebase.

**Acceptance Criteria:**
- The `VideoSummarizationService` constructor is updated to accept a `ResourceReader` instance as a parameter.
- The internal `new ResourceReader()` call is removed from the `VideoSummarizationService` constructor.
- The main application entry point (likely in `Povzetkar` or a `Main` class) is updated to create and inject the `ResourceReader` instance into `VideoSummarizationService`.
- The application compiles and all tests pass without any regressions.

### **Task 5 [POV-33]: Extract Summary File Writing to a Dedicated Class**

**Title:** `refactor(service): Extract summary file writing to a dedicated SummaryFileAppender class`

**Description:**
This task addresses a violation of the DRY principle in `VideoSummarizationService` where the logic for appending summaries with separators (`---`) was duplicated. A new public class, `SummaryFileAppender`, will be created to encapsulate this responsibility, simplifying the main service and improving maintainability.

**Acceptance Criteria:**
- The `FileWriter` inner interface is moved out of `VideoSummarizationService` and becomes a new top-level public interface in the `si.jumis.service` package.
- A new public class `SummaryFileAppender` is created in the `si.jumis.util` package.
- The `SummaryFileAppender` class constructor accepts the new top-level `FileWriter` interface and a `Path`. It internally manages whether a separator is needed based on the initial file state.
- The `summarizeVideoBatch` and `summarizeFromUrls` methods in `VideoSummarizationService` are refactored to use an instance of `SummaryFileAppender`.
- The duplicated separator logic is completely removed from `VideoSummarizationService`.
- The application's file output for summaries remains identical to the previous implementation.

### **Task 6 [POV-34]: Extract Video Fetching Logic into a New Service**

**Title:** `refactor(service): Extract video fetching logic into NewVideoFetcherService`

**Description:**
This task improves adherence to the Single Responsibility Principle by extracting the complex logic for fetching new videos from `VideoSummarizationService`. A new `NewVideoFetcherService` will be created, whose sole responsibility is to determine which videos are new for a given set of authors and a target date.

**Acceptance Criteria:**
- A new `NewVideoFetcherService` class is created in the `si.jumis.service` package.
- The logic from `fetchAllNewVideos` and `fetchVideosForAuthor` in `VideoSummarizationService` is moved to the new service.
- `NewVideoFetcherService` takes `YouTubeDataService` and `ProcessingStateService` as dependencies.
- `VideoSummarizationService` is refactored to use `NewVideoFetcherService` to get the list of new `VideoToProcess` objects.
- The overall application behavior for fetching videos remains unchanged.

### **Task 7 [POV-35]: Extract AI Content Preparation into a New Service**

**Title:** `refactor(service): Extract AI content preparation into ContentCreationService`

**Description:**
This task further improves SRP in `VideoSummarizationService` by extracting the "prompt engineering" logic. A new `ContentCreationService` will be responsible for creating the `com.google.genai.types.Content` object to be sent to the Gemini API, including the decision to use a transcript or a video URL.

**Acceptance Criteria:**
- A new `ContentCreationService` class is created in the `si.jumis.service` package.
- The logic from the `getContent` method in `VideoSummarizationService` is moved to the new service.
- `ContentCreationService` takes `YouTubeTranscriptService` as a dependency.
- `VideoSummarizationService` is refactored to use `ContentCreationService` to get the `Content` object for a given video.
- The logic for deciding to use a transcript based on video duration is now fully contained within `ContentCreationService`.

### **Task 8 [POV-36]: Extract Documentation Generation to a Dedicated Service**

**Title:** `refactor(core): Extract documentation generation to DocumentationService`

**Description:**
This task improves SRP by extracting the complex logic for generating and parsing Markdown documentation (`README.md`, `updates.md`, briefings) from the `Povzetkar` orchestrator class into a new, dedicated `DocumentationService`. This will make `Povzetkar` a cleaner, more focused orchestrator.

**Acceptance Criteria:**
- A new `DocumentationService` class is created in the `si.jumis.service` package.
- The methods `updateDocumentationFiles`, `generateReadmeContent`, `findAndParseBriefings`, `parseBriefingFile`, and related helpers are moved from `Povzetkar` to `DocumentationService`.
- `Povzetkar` is refactored to delegate all documentation-related work to an instance of `DocumentationService`.
- The existing parsing logic is moved as-is; making it more robust is deferred to a future task.

### **Task 9 [POV-37]: Centralize Application Configuration**

**Title:** `refactor(config): Centralize all configuration into a properties file`

**Description:**
This task consolidates all runtime configuration into a single `povzetkar.properties` file. This includes command-line arguments (`--use-case`, etc.) and hardcoded paths (Git repository, author list file). This change will simplify application startup, improve manageability, and remove the need for manual command-line argument parsing, preparing the application for a smoother migration to Quarkus.

**Acceptance Criteria:**
- A new `AppConfig` class is created in a `si.jumis.config` package to load and provide properties from `povzetkar.properties`.
- The `Main.java` class is refactored to use `AppConfig` instead of parsing command-line arguments. The `parseRunConfiguration` method is removed.
- The hardcoded path constants in `Povzetkar.java` and `VideoSummarizationService.java` are removed.
