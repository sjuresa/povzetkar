## 1. Overarching Goal: Operational Excellence & Technical Modernization

Version 0.7.0 aims to mature the platform from a "working prototype" to a robust, observable, and manageable system. The scope has been strictly limited to **essential operational fixes** and the **Quarkus 3.27.x LTS update** to clear the path for the Standalone Deployment (v0.8) as quickly as possible.

## 2. Rationale for Key Decisions

### 2.1. Updating to Quarkus 3.27.x LTS

We are prioritizing the update to **Quarkus 3.27.x LTS**.

**Rationale:**
*   **Stability:** As an LTS (Long Term Support) release, 3.27.x provides the stability required for "Operational Excellence" while bringing the stack up to date.
*   **Foundation:** Updating now ensures that our Docker containerization work in v0.8 is built on a modern, supported foundation.

### 2.2. Addressing Orchestration "Blind Spots"

We identified that content items can get stuck in a `PENDING` state if the orchestrator crashes, and that logging is currently spammy yet insufficient.

**Rationale:**
*   **Data Integrity:** A system that silently ignores stuck items is not reliable. Treating `PENDING` items similarly to `RETRY_LATER` ensures eventual consistency.
*   **Observability:** Deduplicating logs and adding metadata (duration, URL) drastically reduces the time needed to debug issues in production.

### 2.3. Enhancing Administrator Control

We are introducing the ability to enable/disable specific topics and granularly control the orchestration process.

**Rationale:**
*   **Operational Flexibility:** Administrators need the ability to pause processing for a specific topic (e.g., if a source is spamming) without stopping the entire system.
*   **Process Granularity:** Separating the "Summarization" and "Briefing" phases allows for more targeted operations (e.g., re-generating briefings without re-fetching content).
*   *Note:* We removed the requirement for a specific single-topic orchestration endpoint, as the enable/disable mechanism combined with the main orchestrator trigger provides sufficient control for the current needs.

### 2.4. Enhancing Observability and Error Handling

We expanded the scope of the Admin UI task to include persistence of error codes and transcripts.

**Rationale:**
*   **Actionable Insights:** The Admin UI is not useful if it only shows "Failed". Persisting specific error codes (e.g., `RATE_LIMIT`, `TRANSCRIPT_UNAVAILABLE`) allows administrators to understand *why* something failed.
*   **Efficiency:** Persisting transcripts and implementing "Smart Retry" prevents wasteful API calls when re-processing items that failed in later stages (e.g., summarization).

### 2.5. Deferring Advanced Features for Speed

Initially, we considered including "Time Period Briefings" and "Advanced Rate Limiting". However, to accelerate the timeline for **v0.8 (Standalone Deployment)**, we have decided to defer these complex features to a later version (v0.9).

**Rationale:**
*   **Focus:** The priority is to get the application deployable as a standalone artifact. Adding complex logic now delays that goal.
*   **Risk Reduction:** Reducing the scope of v0.7.0 minimizes the chance of introducing new bugs before the major deployment milestone.

### 2.6. Deferring Spikes

Research tasks (Transactional Testing, Agent Context) are deferred to v0.9 to focus purely on execution tasks.

## 3. Testing Strategy

*   **UI Testing:** We will continue to improve the Admin UI tests, ensuring assertions cover the new data fields (duration, dates).
*   **Orchestration Testing:** Specific tests will be written to simulate "stuck" PENDING items and verify they are recovered.
