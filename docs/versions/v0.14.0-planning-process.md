# Version 0.14.0 Planning Process: Output Mastery & UX Refinement

**Status:** Initial Task List (Planning Phase)
**Date:** 2026-03-25

## Introduction
This document details the iterative planning process for Version 0.14.0. Building on the "UX Foundation" established in v0.13.0, this version focuses on "Output Mastery"—refining how users trigger work, manage results, and experience the application's premium value proposition.

## Phase 1: Strategic Evaluation & Feature Selection

During the transition from v0.13.0 to v0.14.0, we evaluated the remaining roadmap items and user feedback regarding the "MVP feeling" of orchestration.

### Discussion 1: Prioritizing User UX over Admin Roles
*   **Initial Proposal:** Focus heavily on User/Role management UI to complete the security story.
    *   **Pros:** Completes the administrative "Command Center".
    *   **Cons:** The core user flow for triggering briefings (the "Play" button) remains a "black box" with no configuration.
*   **Final Decision:** **Pivoted to UX and Orchestration Control.** We decided to prioritize the "Trigger Dialog" (Run Now v2) and Topic UX. We concluded that empowering the user to control *what* is summarized and *when* is higher value than internal user management at this stage.

## Phase 2: Scoping and Interaction Design

### Discussion 2: Refining Topic Source Intake
*   **Initial Proposal:** Show all sources in the Topic form, similar to v0.13.0.
    *   **Pros:** Consistent with existing patterns.
    *   **Cons:** As the source library grows, the list becomes unmanageable. It clutters the "Topic Creation" experience.
*   **Final Decision:** **Search-Based Persistent List.**
    *   The Topic form now shows *only* selected sources.
    - Adding new ones is done via a search popover/modal.
    - **Justification:** This keeps the "Topic View" clean while allowing power users to manage large libraries efficiently.

### Discussion 3: Status Overrides (Owner vs. Admin)
*   **Decision:** We debated if a regular Topic owner should be able to force a retry (`FAILED` -> `RETRY_LATER`).
*   **Outcome:** **Admin Only.** We restricted this to the `ADMIN_JOB_UPDATE` permission (Task POV-155) to prevent accidental server load from users repeatedly forcing retries on broken feeds.

## Phase 3: Testing & Use Case Philosophy

### Discussion 4: Bridging Stories to Specs
*   **Problem:** Functional stories in `01_functional_requirements.md` were too high-level for complex UI flows like the new Trigger Dialog.
*   **Decision:** **Introduced `use_cases.md`.**
    *   We created **[use_cases.md](../analysis/use_cases.md)** to document the "Happy Path" for v0.14.0 features.
    *   **Justification:** This serves as the single source of truth for both implementation and Playwright E2E test scripts, ensuring higher quality and better alignment between UI and API.

## Phase 4: Backlog & Retrospective Integration

### Discussion 5: Addressing Technical Debt
*   **Decision:** Based on the **[v0.13.0-retrospective.md](../retrospectives/v0.13.0-retrospective.md)**, we included:
    *   **`matchMedia` mocking**: To fix Vitest failures on responsive components.
    *   **Docker Hardening**: Addressing specific CVEs discovered during v0.13 cycle.
    *   **Admin Jobs Pagination**: From the improvements backlog, integrated into the new status management view.

## Final Planning Outcome
The resulting task list (**POV-153 to POV-158**) focuses on:
1.  **Orchestration Transparency**: (Trigger Dialog, Status Overrides).
2.  **Scalable UI**: (Source Search, Persistent Lists).
3.  **Premium Experience**: (High-Converting Landing Page, Versioning Metadata).
4.  **Security & Quality**: (Docker CVEs, JaCoCo Coverage).
