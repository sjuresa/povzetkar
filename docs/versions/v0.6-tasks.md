This document lists the tasks for version 0.6. The primary goal is to **migrate the entire core workflow into the new Quarkus application**, making it fully autonomous. This includes fetching videos, creating summaries, generating briefings, and publishing to Git. This version also completes the implementation of **full multi-topic support**, building on the foundations laid in v0.5.

### **Task 1 [POV-55]: Update High-Level Design Documents**

**Title:** `docs: Align architecture and database design with accelerated roadmap`

**Description:**
Update the core design documents to reflect the new, accelerated migration strategy where the Quarkus application becomes fully autonomous in v0.6. This ensures the documentation is consistent before implementation begins.

**Acceptance Criteria:**
- `docs/overview/architecture_overview.md` is updated to show the Quarkus app as the sole component, with the legacy app being decommissioned at the end of this version.
- `docs/overview/database_design.md` is updated to include the `Summary` and `Briefing` entities and their relationships.

### **Task 2 [POV-56]: Extend Data Model for Summaries and Briefings**

**Title:** `feat(model): Create Summary and Briefing JPA entities`

**Description:**
Extend the database schema to support the storage of summaries and daily briefings, which are central to the new workflow.

**Acceptance Criteria:**
- A `Summary` JPA entity is created, linked to a `ContentItem`. It will store the generated summary text and status.
- A `Briefing` JPA entity is created, which will have a date and a many-to-many relationship with `Summary` entities.
- Database migration scripts are updated to reflect the new schema.

---

### **Task 3 [POV-57]: Migrate Full Channel Detail Fetching**

**Title:** `feat(quarkus): Migrate full channel detail fetching to Quarkus`

**Description:**
Migrate the remaining logic from the legacy `AuthorService` (i.e., calling `YouTubeDataService` to get channel details) into a new Quarkus service. This service will be responsible for populating and periodically refreshing channel details in the database.

**Acceptance Criteria:**
- A new `ChannelDetailService` is created in Quarkus.
- This service fetches details (name, description, subscriber count) from the YouTube API for all channels in the database that are missing this information.
- An admin endpoint (e.g., `POST /api/v1/channels/enrich`) is created to trigger this service on demand for initial population.
- A `@Scheduled` method is added to the service to periodically refresh the details of existing channels (e.g., weekly).

### **Task 4 [POV-58]: Implement Core Summarization Logic**

**Title:** `feat(core): Implement summarization and transcript service`

**Description:**
Migrate the core AI-related logic into a dedicated Quarkus service. This service will be responsible for taking a video, producing a summary, and managing the outcome.

**Acceptance Criteria:**
- A new `SummarizationService` is created in Quarkus.
- It takes a `ContentItem` as input.
- It contains the logic migrated from `YouTubeTranscriptService` to fetch transcripts.
- It contains the logic migrated from `ContentCreationService` to prepare the prompt for the GenAI model.
- It orchestrates the calls to the transcript and GenAI services within a `try-catch` block.
- **On success:**
    - It creates and persists a `Summary` entity linked to the `ContentItem`.
    - It updates the `ContentItem`'s status to `COMPLETED`.
- **On transient failure** (e.g., transcript not yet available):
    - It updates the `ContentItem`'s status to `RETRY_LATER`.
    - It logs the error as a warning.
- **On persistent or unrecoverable failure** (e.g., repeated GenAI error, invalid video):
    - It updates the `ContentItem`'s status to `FAILED`.
    - It logs the error as an error.

### **Task 5 [POV-59]: Implement Scheduled Orchestrator**

**Title:** `feat(core): Create scheduled service for the core workflow`

**Description:**
Create the heart of the new application: a scheduled service that automates and orchestrates the entire workflow, from fetching new videos to publishing the final briefing.

**Acceptance Criteria:**
- A new `@ApplicationScoped` service with a `@Scheduled` method is created, configurable via `application.properties`.
- On schedule, the service performs the following steps for each topic:
    1. Fetches new videos from the YouTube API for all channels in the topic, creating `ContentItem` records with `PENDING` status. This replaces the logic from `NewVideoFetcherService`.
    2. For each new `ContentItem`, it calls the `SummarizationService` (from Task 4).
    3. **After the current batch of new videos has been processed**, the orchestrator proceeds to the briefing stage for the relevant time period (e.g., today's date).
    4. It then calls the `BriefingService` to generate or regenerate the briefing for that entire period.
    5. As the final step, it calls the `GitPublishingService` to publish the generated briefing.

### **Task 6 [POV-60]: Implement Briefing and Git Publishing**

**Title:** `feat(reporting): Implement briefing generation and Git publishing`

**Description:**
Create the services for the final output stage of the application. These services will be called by the main orchestrator (from Task 5) to generate and publish daily briefings.

**Acceptance Criteria:**
- A new `BriefingService` is created. It takes a time period (e.g., a `LocalDate`) as input.
- The service queries the database for **all** `Summary` entities within that period.
- It creates a new `Briefing` entity (or updates an existing one for that period), ensuring it is linked to all retrieved summaries. This allows for briefings to be regenerated and updated with new content.
- A new `GitPublishingService` is created, migrating logic from the legacy `Povzetkar` and `DocumentationService` classes.
- This service takes a `Briefing` entity, generates the corresponding markdown file.
- It uses `JGit` to commit and push the new/updated briefing file to the configured Git repository for the relevant topic.

### **Task 7 [POV-61]: Decommission Legacy Workflow**

**Title:** `chore(legacy): Remove and archive the old application's core logic`

**Description:**
With the entire workflow now autonomous in Quarkus, the old application's `main` method and core services can be removed, completing the migration.

**Acceptance Criteria:**
- The `main` method in the legacy `Povzetkar` class is emptied or removed.
- The legacy services (`VideoSummarizationService`, `NewVideoFetcherService`, `DocumentationService`, `AuthorService`, etc.) are deleted.
- The `RUNBOOK.md` is updated to reflect that the application now runs entirely as a Quarkus service, with no manual triggers needed.
