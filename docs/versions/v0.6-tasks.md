This document lists the tasks for version 0.6. The primary goal is to **migrate the entire core workflow into the new Quarkus application**, making it fully autonomous. This includes fetching videos, creating summaries, generating briefings, and publishing to Git. This version also completes the implementation of **full multi-topic support**, building on the foundations laid in v0.5.

### **Task 3 [POV-58]: Implement User Entity and Update Topic (Completed)**

**Title:** `feat(model): Introduce User entity and make Topic multi-tenant`

**Description:**
Introduce the `User` entity as the root of data ownership. The `Topic` entity will be modified to belong to a `User`, and its name will no longer be globally unique, but unique per user.

**Acceptance Criteria:**
- A new `User` JPA entity is created. It includes an `active` boolean field, defaulting to `true`.
- The `Topic` entity is modified to have a `ManyToOne` relationship with `User`.
- The `unique=true` constraint on `Topic.name` is removed and replaced with a table-level composite unique constraint on (`user_id`, `name`).
- A new Flyway migration script (e.g., `V3__add_users_and_update_topics.sql`) is created to:
    - Create the `users` table, including an `active` column with a default value.
    - Add a `user_id` foreign key column to the `topics` table.
    - Drop the old unique constraint on `topics.name` and add the new composite unique constraint.
- `docs/sdlc/04_database_design.md` is updated to reflect these changes.

### **Task 8 [POV-62]: Implement Core Summarization Logic (Completed)**

**Title:** `feat(core): Implement summarization and transcript service`

**Description:**
Migrate the core AI-related logic into a dedicated Quarkus service. This service will be responsible for taking a video, producing a summary, and managing the outcome.

**Acceptance Criteria:**
- A new `SummarizationService` is created in Quarkus.
- It takes a `ContentItem` as input.
- It contains the logic migrated from `YouTubeTranscriptService` to fetch transcripts.
- It contains the logic migrated from `ContentCreationService` to prepare the prompt for the GenAI model.
- It orchestrates the calls to the transcript and GenAI services within a `try-catch` block.
- **On success:**
    - It creates and persists a `Summary` entity linked to the `ContentItem`.
    - It updates the `ContentItem`'s status to `COMPLETED`.
- **On transient failure** (e.g., transcript not yet available):
    - It updates the `ContentItem`'s status to `RETRY_LATER`.
    - It logs the error as a warning.
- **On persistent or unrecoverable failure** (e.g., repeated GenAI error, invalid video):
    - It updates the `ContentItem`'s status to `FAILED`.
    - It logs the error as an error.

### **Task 9 [POV-63]: Implement Scheduled Orchestrator and Briefing Service**

**Title:** `feat(core): Create scheduled orchestrator and briefing service`

**Description:**
Implement the final steps of the automated workflow: a service to generate briefings from summaries, and a scheduled orchestrator to run the entire process from content fetching to briefing creation.

**Acceptance Criteria:**
- The `Briefing` JPA entity is modified to include a `ManyToOne` relationship to the `Topic` entity.
- A new `BriefingService` is created. It takes a `Topic` and a time period (e.g., a `LocalDate`) as input.
- The `BriefingService` queries the database for all `Summary` entities for the given topic within that period.
- It uses the GenAI service to create a meta-summary from the collected summaries.
- It creates a new `Briefing` entity (or updates an existing one), linking it to the parent `Topic` and all relevant summaries, then persisting it.
- Update Flyway migration script to add the `topic_id` foreign key column to the `briefings` table.
- A new scheduled orchestrator service (`OrchestratorService`) is created with a `@Scheduled` method, configurable via `application.properties`.
- On schedule, the orchestrator performs the following steps:
    1. Iterates through all active `User` entities.
    2. For each user, iterates through all their `Topic` entities.
    3. For each topic, it fetches new content from the relevant source APIs for all associated content sources, creating `ContentItem` records with `PENDING` status.
    4. For each new `ContentItem`, it calls the `SummarizationService` (from Task 8). **These calls should be executed in parallel** to improve performance.
    5. The orchestrator **waits for all parallel summarization tasks for the current batch to complete** before proceeding to the briefing stage.
    6. It then calls the `BriefingService` to generate or regenerate the briefing for that topic and period.
- The `docs/sdlc/04_database_design.md` document is updated to reflect the new relationship between the `Briefing` and `Topic` entities.

### **Task 10 [POV-64]: Implement Simple HTML UI for Briefings**

**Title:** `feat(ui): Implement simple HTML interface for briefing review`

**Description:**
Create a simple, server-side rendered web interface for reviewing generated briefings. The interface will be structured to reflect the multi-tenant data model (users have topics, which have briefings). This provides immediate value and serves as a foundation for a more advanced GUI.

**Acceptance Criteria:**
- The `quarkus-qute` dependency is added to the `pom.xml` of the `quarkus-app` module.
- A new JAX-RS resource (e.g., `BriefingWebResource`) is created to handle HTML requests.
- Three endpoints are implemented:
    - `GET /ui/`: Serves as the main entry point, displaying a list of topics grouped by user. Each topic is a link to its briefings page.
    - `GET /ui/topics/{topicId}/briefings`: Displays a list of all briefings for a specific topic, grouped by date, with links to their detail pages.
    - `GET /ui/briefings/{briefingId}`: Displays the details of a specific briefing, including its meta-summary and a list of all associated summaries with their text.
- Corresponding Qute templates (e.g., `topics.html`, `briefings-by-topic.html`, `briefing-detail.html`) are created in `src/main/resources/templates` to render the data.
- The interface is styled with minimal, clean CSS to ensure readability.

### **Task 11 [POV-65]: Refactor Orchestration and Briefing Generation**

**Title:** `refactor(core): Decouple briefing generation and add robustness`

**Description:**
Refactor the orchestration and briefing generation logic to make it more robust, flexible, and resilient. The initial migration revealed that the sequential legacy approach is insufficient for a parallel, multi-tenant system. This task decouples briefing generation from content fetching and adds support for date ranges and error handling.

**Acceptance Criteria:**
- **Briefing Generation Decoupling:**
    - The `OrchestratorService` is refactored. The call to `BriefingService` is removed from the main content processing flow for a topic.
    - A new, separate scheduled method (e.g., `generateBriefingsScheduled`) is added to `OrchestratorService` that runs *after* the content processing orchestration.
    - This new method iterates through all topics and calls `BriefingService` to generate briefings for any dates that have summaries but no corresponding briefing yet.
- **Support for Date Ranges:**
    - The `BriefingService` is modified to accept a start and end date (`LocalDate startDate`, `LocalDate endDate`).
    - The `OrchestratorService` is updated to allow manual triggering of briefing generation for a specific date range via an API endpoint.
- **Resilience to Transient Errors:**
    - A new `briefing_status_enum` (`PENDING`, `COMPLETED`, `FAILED`) is created and added to the `briefings` table via a Flyway script.
    - When `BriefingService` starts, it creates a `Briefing` entity with `PENDING` status.
    - If a transient error occurs during meta-summary generation (e.g., GenAI API returns 503), the status remains `PENDING`, and the error is logged. The next scheduled run will re-attempt generation for all `PENDING` briefings.
    - On success, the status is updated to `COMPLETED`.
    - On persistent failure, the status is updated to `FAILED`.
- **Documentation Update:**
    - `docs/sdlc/04_database_design.md` is updated with the new `briefing_status_enum` and the corresponding column in the `briefings` table.
    - `docs/RUNBOOK.md` is updated with instructions for the new manual briefing generation endpoint.
