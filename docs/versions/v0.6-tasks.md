### **Task 1: Implement Video Ingestion Service in Quarkus**

**Title:** `feat(ingestion): Create service to fetch and persist new videos`

**Description:**
Create a new, topic-aware service in the Quarkus application that replicates the logic of `NewVideoFetcherService`. It will query the database for state based on a given topic, fetch new videos, and persist them.

**Acceptance Criteria:**
- A new `IngestionService` is created in the Quarkus app.
- The service accepts a topic name and fetches all `Channel` entities associated with that topic.
- For each channel, it queries the `content_items` table to find the `published_at` timestamp of the last `COMPLETED` video.
- It uses this timestamp to call the YouTube API and fetch newer videos.
- New videos are persisted as `ContentItem` records with a `processing_status` of `PENDING`.
- The service handles the initial case where no previous state exists for a channel.

### **Task 2: Expose Ingestion Logic via REST API**

**Title:** `feat(api): Create POST /api/v1/topics/{name}/ingestion/fetch-new endpoint`

**Description:**
Expose the `IngestionService` logic via a REST endpoint that the old application can call. This endpoint will trigger the ingestion process and return the list of newly found videos.

**Acceptance Criteria:**
- A new JAX-RS resource is created.
- It exposes a `POST /api/v1/topics/{name}/ingestion/fetch-new` endpoint.
- The endpoint triggers the `IngestionService` for the specified topic.
- On success, it returns a `200 OK` with a JSON array of DTOs representing the newly created `ContentItem` records. The DTOs should contain enough information for the old application to proceed (e.g., video ID, title, URL, author name, etc.).

### **Task 3: Refactor Legacy App to Delegate Video Fetching**

**Title:** `refactor(legacy): Delegate video fetching to Quarkus API`

**Description:**
Modify the original application to stop fetching videos directly. Instead, it will call the new Quarkus API and use the results. This is the "strangling" step.

**Acceptance Criteria:**
- Add a REST client dependency to the legacy application's `pom.xml` (e.g., `java.net.http.HttpClient` or a library).
- In `VideoSummarizationService`, the call to `newVideoFetcherService.fetchAllNewVideos` is replaced with a REST client call to `POST /api/v1/topics/{name}/ingestion/fetch-new`, where `{name}` is determined from the application's current configuration.
- The DTOs returned from the API are correctly deserialized into a list of objects that the rest of the `summarizeFromAuthors` method can process.
- The `NewVideoFetcherService` and its direct dependency `ProcessingStateService` can now be marked as `@Deprecated` in the legacy app, as their primary responsibility has been migrated.

### **Task 4: Implement Integration Tests**

**Title:** `test(ingestion): Create integration tests for the ingestion endpoint`

**Description:**
Write robust integration tests for the new ingestion endpoint to ensure it works correctly with a real database and mocked external APIs.

**Acceptance Criteria:**
- A new `@QuarkusTest` class is created for the ingestion resource.
- The test uses Testcontainers to provide a real PostgreSQL database.
- The YouTube Data API is mocked (e.g., using WireMock or a custom mock bean) to return predictable video data.
- The test verifies:
  - The endpoint returns a `200 OK`.
  - The correct `ContentItem` records are created in the database with `PENDING` status.
  - The JSON response body matches the expected DTOs.
  - The logic correctly handles both initial fetch and incremental fetch scenarios.
