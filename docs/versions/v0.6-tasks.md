This document lists the tasks for version 0.6. The primary goal is to **migrate the entire core workflow into the new Quarkus application**, making it fully autonomous. This includes fetching videos, creating summaries, generating briefings, and publishing to Git. This version also completes the implementation of **full multi-topic support**, building on the foundations laid in v0.5.

### **Task 2 [POV-57]: Integrate Flyway for Database Migrations (Completed)**

**Title:** `chore(db): Integrate Flyway for database schema management`

**Description:**
Introduce a robust database migration tool to manage schema changes systematically. Flyway is chosen for its simplicity and strong integration with Quarkus. This replaces manual schema updates.

**Acceptance Criteria:**
- The `quarkus-flyway` dependency is added to the `pom.xml`.
- Flyway is configured in `application.properties` to run migrations on startup.
- An initial migration script (`V1__create_initial_schema.sql`) is created based on the schema defined in v0.5 (Topic, Channel, ContentItem tables).

### **Task 3 [POV-58]: Implement User Entity and Update Topic (Completed)**

**Title:** `feat(model): Introduce User entity and make Topic multi-tenant`

**Description:**
Introduce the `User` entity as the root of data ownership. The `Topic` entity will be modified to belong to a `User`, and its name will no longer be globally unique, but unique per user.

**Acceptance Criteria:**
- A new `User` JPA entity is created. It includes an `active` boolean field, defaulting to `true`.
- The `Topic` entity is modified to have a `ManyToOne` relationship with `User`.
- The `unique=true` constraint on `Topic.name` is removed and replaced with a table-level composite unique constraint on (`user_id`, `name`).
- A new Flyway migration script (e.g., `V3__add_users_and_update_topics.sql`) is created to:
    - Create the `users` table, including an `active` column with a default value.
    - Add a `user_id` foreign key column to the `topics` table.
    - Drop the old unique constraint on `topics.name` and add the new composite unique constraint.
- `docs/sdlc/04_database_design.md` is updated to reflect these changes.

**Title:** `refactor(db): Create a single, consolidated V1 schema migration script`

**Description:**

### **Task 7 [POV-61]: Migrate Full Content Source Detail Fetching**

**Title:** `feat(quarkus): Migrate full content source detail fetching to Quarkus`

**Description:**
Migrate the remaining logic from the legacy `AuthorService` (i.e., calling `YouTubeDataService` to get channel details) into a new Quarkus service. This service will be responsible for populating and periodically refreshing content source details in the database.
**Acceptance Criteria:**
- A new `ContentSourceDetailService` is created in Quarkus.
- This service fetches details (name, description, subscriber count) from the YouTube API for all content sources in the database that are missing this information.
- An admin endpoint (e.g., `POST /api/v1/content-sources/enrich`) is created to trigger this service on demand for initial population.
- A `@Scheduled` method is added to the service to periodically refresh the details of existing content sources (e.g., weekly).

### **Task 8 [POV-62]: Implement Core Summarization Logic**

**Title:** `feat(core): Implement summarization and transcript service`

**Description:**
Migrate the core AI-related logic into a dedicated Quarkus service. This service will be responsible for taking a video, producing a summary, and managing the outcome.

**Acceptance Criteria:**
- A new `SummarizationService` is created in Quarkus.
- It takes a `ContentItem` as input.
- It contains the logic migrated from `YouTubeTranscriptService` to fetch transcripts.
- It contains the logic migrated from `ContentCreationService` to prepare the prompt for the GenAI model.
- It orchestrates the calls to the transcript and GenAI services within a `try-catch` block.
- **On success:**
    - It creates and persists a `Summary` entity linked to the `ContentItem`.
    - It updates the `ContentItem`'s status to `COMPLETED`.
- **On transient failure** (e.g., transcript not yet available):
    - It updates the `ContentItem`'s status to `RETRY_LATER`.
    - It logs the error as a warning.
- **On persistent or unrecoverable failure** (e.g., repeated GenAI error, invalid video):
    - It updates the `ContentItem`'s status to `FAILED`.
    - It logs the error as an error.

### **Task 9 [POV-63]: Implement Scheduled Orchestrator**

**Title:** `feat(core): Create scheduled service for the core workflow`

**Description:**
Create the heart of the new application: a scheduled service that automates and orchestrates the entire workflow, from fetching new videos to publishing the final briefing.

**Acceptance Criteria:**
- A new `@ApplicationScoped` service with a `@Scheduled` method is created, configurable via `application.properties`.
- On schedule, the service performs the following steps:
    1. Iterates through all active `User` entities.
    2. For each user, iterates through all their `Topic` entities.
    3. For each topic, it fetches new videos from the YouTube API for all associated content sources, creating `ContentItem` records with `PENDING` status.
    4. For each new `ContentItem`, it calls the `SummarizationService` (from Task 8). **These calls should be executed in parallel** to improve performance.
    5. The orchestrator **waits for all parallel summarization tasks for the current batch to complete** before proceeding to the briefing stage.
    6. It then calls the `BriefingService` to generate or regenerate the briefing for that entire period.
    7. As the final step, it calls the `GitPublishingService` to publish the generated briefing.

### **Task 10 [POV-64]: Implement Briefing and Git Publishing**

**Title:** `feat(reporting): Implement briefing generation and Git publishing`

**Description:**
Create the services for the final output stage of the application. These services will be called by the main orchestrator (from Task 9) to generate and publish daily briefings.

**Acceptance Criteria:**
- A new `BriefingService` is created. It takes a time period (e.g., a `LocalDate`) as input.
- The service queries the database for **all** `Summary` entities within that period.
- It creates a new `Briefing` entity (or updates an existing one for that period), ensuring it is linked to all retrieved summaries. This allows for briefings to be regenerated and updated with new content.
- A new `GitPublishingService` is created, migrating logic from the legacy `Povzetkar` and `DocumentationService` classes.
- This service takes a `Briefing` entity, generates the corresponding markdown file.
- It uses `JGit` to commit and push the new/updated briefing file to the configured Git repository for the relevant topic.
