## 1. Overarching Goal: The Architectural Skeleton

The primary goal of version 0.5 is not to deliver new user-facing features. Instead, its sole purpose is to construct the **"Architectural Skeleton"** of the new Quarkus-based application. This involves:

1.  **Establishing the Foundation:** Setting up the project structure, dependencies, database, and CI/CD pipeline.
2.  **Validating the Core Stack:** Proving that all fundamental components (HTTP server, REST layer, dependency injection, ORM, database connection) work together seamlessly.
3.  **Preparing for Migration:** Creating a stable, tested, and verifiable base upon which the "Strangler Fig" migration can begin in v0.6.

Every task in this version was chosen to support these goals with minimal waste and maximum confidence.

## 2. Rationale for Key Tasks

### Task 1-3: Foundational Setup

These tasks (`Foundational Quarkus App & DB Setup`, `Health Check & Initial Integration Test`, `Implement Core Data Entities`) are the essential building blocks. The most critical deliverable here is the **Testcontainers-based integration test**. This test provides undeniable proof that the application can start, connect to a real database, and is ready for further development. It's a crucial risk-reduction step.

### Task 4: One-Time, Direct-to-DB Migration Script

During planning, we decided that the initial data population should happen via a **direct database connection**.

**Rationale:**
*   **Pragmatism:** A migration script is a one-time, throwaway tool. A direct JDBC connection is the simplest and most efficient way to perform a bulk data load.
*   **Focus:** This approach keeps the focus of v0.5 on building the *application's* skeleton, while the migration script remains a separate, simple utility.
*   **Phased Migration:** It was determined that migrating the application's *state* (`processing_state.properties`) at this stage is premature. State management will remain the responsibility of the legacy application for now. Therefore, this script will only migrate static configuration data (topics and channels) needed for the next step.

### Task 5: Vertical Slice Validation API
The `GET /api/v1/topics/{name}/channels` endpoint is not just a test; it's the **first real replacement of existing logic** (the file-based `AuthorService`). By implementing this topic-aware API *after* the data has been migrated, we are forced to validate the entire request-response lifecycle against a realistic dataset.

### Task 6: The First "Strangling" Step
The final task of this version is to refactor the legacy `AuthorService` to call the new API. This is a crucial decision.

**Rationale:**
*   **Ultimate Validation:** This provides the ultimate proof that the new architecture is not just technically sound but also practically usable from the old application.
*   **Immediate Value:** It immediately centralizes the "source of truth" for the *list* of channels into the database, removing the need for file-based configuration in the old application. This is a perfect example of an incremental migration.
*   **Risk Reduction:** It de-risks future migration steps (like in v0.6) by proving the inter-application communication works before more complex logic is migrated.

`HTTP Request -> JAX-RS Resource -> Service Layer (optional) -> Panache Repository -> Database`

This confirms the architectural skeleton is a functioning system ready to take on real responsibilities.

This pragmatic choice accelerates the setup process without compromising the integrity of the new application, as all future interactions will occur through proper, permanent APIs starting in v0.6.
