# The Mandatory Workflow for Code Changes

For every request that modifies code, follow this exact sequence. The plan → approval gate (Steps 3–4) is never skipped or merged.

**Step 1: Define the Task in `agent_logs/task.md`**

- If a task definition exists for the current task, read it and confirm understanding. Check its Status header first: if it describes an already-completed task, a new task starts at checklist step 2.0 (Brainstorm).
- If none exists, create one from the user's request. All subsequent work is grounded in this document.
- `task.md` carries two standing sections, maintained throughout the task:
  - `## Time Log` — phase timestamps in local Europe/Ljubljana time, `[YYYY-MM-DD HH:MM CET]` or `[YYYY-MM-DD HH:MM CEST]` — the label that applies on that date (CEST while daylight saving time is in effect) — recorded **at the moment** the boundary happens: Brainstorm started, Task definition approved (= Brainstorm completed — the Brainstorm ends with the PO's approval of its output, not with the interview), Plan approved, Implementation started/completed, Code review round N started/completed, Pushed, PR-loop fix started/completed, Deploy started/completed, Task completed. Two kinds of waiting are logged explicitly:
    - **Machine waits ≥ 10 min** (full suite, build, CI run, local Trivy, waiting for the PR reviewer) — a `started`/`completed` pair tagged `[wait: suite]`, `[wait: CI]`, `[wait: reviewer]` etc.; they count as **Testing** (Step 7). Shorter waits are not logged separately.
    - **PO waits** are mostly task-related checking, thinking and alignment. The agent reads the clock when it ends a turn that waits for a PO answer and again when the answer arrives; a wait of **≥ 30 min** is logged as `[paused: PO]` with its duration. A pause the PO declares is logged as `[paused: PO, declared]` with its duration, or at its start with `resumed (declared pause)` at its end — gap markers; what is booked is decided at the YouTrack task record (Step 7).
  - `## Deviations` — every decision that departs from the approved plan, appended at decision time with its rationale. This feeds the walkthrough and retrospective.

*Pausing, resuming and session hand-over* — there is one `task.md` slot and one working tree, so one task is executed at a time (WIP = 1).

- **Pause (the task is preempted by another one):** commit the work in progress on the task branch (a `wip:` commit, undone on resume — see below) — never leave it uncommitted or stashed, or it leaks into the next task's branch — then check out the version branch. A `wip:` pause commit is exempt from the suite and review gates (it is never proposed as a finished commit; the pre-commit review later covers the whole branch diff). Set the Status to `Paused — preempted by POV-YYY (<reason>)`, log `[paused: preempted by POV-YYY]` (excluded from the work items), and copy `task.md` to its permanent record `agent_logs/<task id> <task title> task.md` (Step 5). In YouTrack set the State to `Open` and comment the reason; add a "depends on" link only if the task really waits for the other task's result.
- **Resume:** check that the `task.md` slot is free (its task is complete or itself paused), copy the permanent record back, restore the Status, log `resumed`, set YouTrack to `In Progress`. Check out the task branch; only if the last commit is the pause commit (`git log -1 --format=%s` starts with `wip:`), undo it with `git reset HEAD~1` (its changes return to the working tree, unstaged; run `git add -N .` so files it added stay tracked for the autostash); then bring the branch up to date with the current version branch — `git rebase --autostash <version-branch>` if it was never pushed; if it is already pushed (e.g. an open PR), `git merge --autostash <version-branch>` instead (no force-push without the PO's consent); `--autostash` parks and restores the uncommitted changes, which a plain rebase refuses — and re-check the approved plan against what the preempting task changed; record any adjustment in `## Deviations`.
- **Session hand-over (same task, new session):** not a pause. Log `handed over to a new session`; every new session that continues a task logs `session started` as its first action (also after a session that ended without a hand-over); `task.md` stays in place and its Status names the resume point (e.g. "Plan approved — continue at Phase 3"). The new session starts from `task.md` and the plan file, without a new Brainstorm.

**Step 2: Information Gathering & Evidence Collection**

- Identify what must be verified in the codebase to fulfil the request safely, and read it.
- For any code to be modified or removed, find its usages first (declaration → production usages → tests) — see the Change-Impact Checklist in `quality-mandates.md`.
- **Evidence Mandate:** list the specific files and code elements analyzed; the plan may contain only claims grounded in them.

**Step 3: Present Findings & a High-Precision Plan**

- **Findings:** a bulleted list of verified facts from the code.
- **Detailed plan**, organized in phases: exact classes/methods/signatures to create or modify, specific logic details, database migration details (Flyway version and SQL goal), frontend component structure and design tokens.
- **Design justification:** how the change aligns with SOLID, Clean Code, and the existing architecture.
- **Verification strategy** for every major step.
- **Breaking-changes analysis** — or an explicit "No breaking changes identified".
- **Interview archive** whenever a planning interview was held: `| # | Question | Decision | Reasoning |`.

*Self-review* — after the Brainstorm (before the task definition is put up for approval), after the plan (before Step 4), and before the commit or at the end of a larger unit of work (e.g. a plan phase), the agent checks its own output in its own context (no skill, no subagent): every claim, figure and reference against its source, every requirement against the approved task definition, and for a plan also the consistency of its artefacts (`planning_protocol.md` §2.3). Findings and their dispositions go briefly into `## Deviations`. A self-review shares the author's blind spots; it does not replace the pre-commit review.

**Step 4: Await Explicit Approval — and Handle Rejection or Failure**

- Stop. Take no further action (including archiving) until the user explicitly approves ("Yes", "Proceed", "Approved").
- **Invalidated plan** (rejection, user-reported bug, changed requirements): halt immediately, acknowledge, and ask for the reason if unclear. Do not patch the old plan — treat the new information as a new task and re-enter this workflow at Step 1. Do not re-attempt a rejected file modification; wait for new instructions.
- **Knowledge gap** (~2 failed attempts on framework or tooling complexity): stop trial-and-error, state what pattern or knowledge is missing, and propose a research Spike task.
- Failures are acknowledged and analyzed, never apologized for. If a failure reveals a process flaw, propose a protocol fix.

**Step 5: Archive the Approved Plan and Task**

- Write the approved plan verbatim to `agent_logs/<task id> <task title> plan.md`.
- Copy the approved task definition to `agent_logs/<task id> <task title> task.md`.
- These two files are the task's permanent record; there is no separate execution log.

**Step 6: Execute the Plan**

- Execute step by step. Report progress per meaningful unit of work — a completed plan step, or a finding that changes direction — not per tool call. Independent read-only operations may run in parallel.
- Record phase milestones in `## Time Log` and deviations in `## Deviations` as they happen.
- **Unplanned discoveries:** apply checklist step 2.13 (assess criticality → address now, or log to `docs/backlog/improvements.md`); either way, record the outcome in `## Deviations`.
- **Nested sub-plans:** a necessary deviation (e.g., a prerequisite bug) pushes a sub-plan onto a conceptual stack. Execute only the top plan; pop it on verified completion and announce resumption of the parent plan and its next step.
- Recommended, not mandated: a fast syntactic gate (`tsc`, `mvn compile`) at the end of each phase touching that layer. The full suite (Step 7) is the only hard gate.

**Step 7: Close Out the Task**

- Run **Final Behavioral Verification** per `docs/protocols/verification.md` — the full suite for every touched layer, not task-related tests only.
- Update `CHANGELOG.md` under `[Unreleased]` (checklist 2.6) — every task, process and tooling tasks included: process/documentation changes under `### Documentation`, security fixes under `### Security`. An entry says what changed for the reader; verification figures stay in the walkthrough. The release editorial cleanup (checklist 3.4) may consolidate internal entries.
- Write `docs/versions/vX.Y.Z/POV-XXX-walkthrough.md`: what was done, planned vs. actual scope, time delta (from the Time Log in `agent_logs/task.md`), deviations, and **Traceability** — US/UC/TC IDs or `N/A — <reason>` (machine-validated by `validate-planning.py`). Verification evidence (red/green demonstrations, sweep results) belongs here. The walkthrough, retrospective, version hub and every PR text or review reply are public — `docs/protocols/public-content.md` applies (plain issue IDs, no environment values). **A fact or figure is stated once, in the walkthrough** (test counts, review findings, times, scope changes); the CHANGELOG, the version retrospective and the hub refer to it.
- Append this task's block to `docs/versions/vX.Y.Z/retrospective.md` under `## Task Notes` (checklist 2.11): **Why it deviated**, **Technical findings**, **Feed-forward** — short; facts by reference to the walkthrough.
- Add the walkthrough row to `docs/versions/vX.Y.Z/version.md`; append systemic lessons to `docs/process/lessons-learned.md`; log non-critical improvements to `docs/backlog/improvements.md`.
- Run the **Master Specification Sync** (checklist 2.14): flip a `(Planned)` US to `(Implemented)`, sync `use_cases.md` / `test_specification.md` or record a justified N/A, run the planning audit.
- Self-review the close-out (*Self-review*, above), then run the **Pre-commit Review** (below, checklist 2.5a) — now, with the suite green and all close-out documents written, so the review covers code *and* documents; before the first commit.
- Copy the final `agent_logs/task.md` — now carrying the complete `## Time Log` and `## Deviations` — over `agent_logs/<task id> <task title> task.md`, replacing the initial copy from Step 5 so the permanent record preserves the full execution history.
- Verify the task's Definition of Done, then propose a commit message per `docs/protocols/commit-conventions.md` and end with: **"I have proposed the commit message. Is anything left before the commit, or shall I commit, push and open the PR?"** Then wait.
- After the PO approves commit and push (checklist 2.9), commit, push and run the PR review loop (Step 8). If the PO deploys within the task, run Pre-deploy Verification (checklist 2.5b) after the push. Once the loop has exited — and the deploy, if any, is done — write the **YouTrack task record** (below, checklist 2.15) — last, so the work items include the PR loop and the deploy. After the commit the walkthrough gets no time or PR-loop/deploy additions (each edit needs a new commit and re-opens the loop); corrections a reviewer asks for in the PR loop are still made. Its time delta covers the task up to the commit; the PR-loop and deploy time live in the Time Log and the work items, deploy evidence (CI run id, rollback tag, smoke check) in `## Deviations` and in an addendum to the walkthrough comment in YouTrack.

*Pre-commit Review* (checklist 2.5a) — every task by default, documentation included:

- `/code-review high` on the whole task diff against the base branch — the **first round is the default** for every task. Only as an exception, with a weighty reason (e.g. a one-line wording fix), may the agent propose skipping it or running it on a reduced scope; the PO decides. Always pass the range `high <base>...HEAD` — without a range the skill reviews only uncommitted changes against HEAD, and a bare branch name (`high v0.19.0`) makes it review that branch against `main`, i.e. the wrong code; the reviewer must state which range it actually reviewed. Before the review run `git add -N .` so new, still untracked files appear in `git diff`, and tell the reviewer to include uncommitted changes (`git diff <base>`). When the diff changes normative documents (protocols, checklist, RUNBOOK), the review also checks them for contradictions, step ordering and rules an agent cannot execute as written.
- Additionally `/security-review` when the task touches authentication, authorization, secrets, cryptography or the attack surface (exposed endpoints, security-relevant configuration, proxy headers).
- **Where it runs:** by default in a subagent (Agent tool), which reviews the diff in its own context and returns only verified findings (`file:line`, severity, proposed fix) — the review is context-heavy. PO approval of this protocol pre-authorises that subagent. Fallback: if the subagent cannot run the review or the session is near full, stop before the commit and ask the PO to run the review in a separate session and paste the findings.
- **Record:** every finding with its disposition (fixed / rejected with a reason) goes into `## Deviations`, a summary into the walkthrough. A skipped or reduced first round goes there too, with its reason and the PO's decision. After fixes, re-run the full suite of the touched layers. A **further round** runs only with the PO's confirmation: after each round, and after each PR-loop fix (Step 8), the agent proposes whether another one is needed, with its reasons — a medium-or-higher defect found in code or normative text, or fixes that changed code or the meaning of normative text, argue for one; findings and fixes only in wording argue against. A further round runs `/code-review high` on the **whole task diff** (`git diff <base branch>`, uncommitted fixes included) — not only on the fixes: fixes introduce defects too, and a re-review of the whole diff also catches what earlier rounds missed and how a fix fits the unchanged text around it.

*YouTrack task record* — `agent_logs/` is gitignored, so the issue is the shared record of the task:

- **State:** `In Progress` when the Brainstorm starts; `Open` while paused (Step 1); `Fixed` at close-out, together with **Fix version** = the current version and **Estimation** from `task.md`.
- **Three comments, copied verbatim from the files** — the task definition (incl. the Brainstorm interview), the approved plan, the walkthrough — each headed with its source file and split into labelled parts (1/2, 2/2) if too long. Read every comment back and compare it with its file; a condensed "verbatim" comment is a defect.
- After writing the record, copy the final `agent_logs/task.md` over its permanent record again, so it holds the PR-loop entries the work items were built from.
- **Task time** is the span from `Brainstorm started` to `Task completed`, logged right before the work items are posted, minus the `[paused: preempted by …]` and `[paused: PO, declared]` intervals. The agent lists the other gaps at once — every `[paused: PO]` entry and every interval between two sessions (the last entry of one session to its successor's `session started`) — and per gap the PO decides: subtract it, subtract N min, or keep it. Nothing else is a gap — in particular not the time between two phase entries. Kept gap time takes the type of the phase it falls in; outside any phase, Development.
- **Work items per phase**, derived from the Time Log: Brainstorm → Plan approved plus close-out documentation as **Documentation**; implementation, fixes between review rounds, PR-loop fixes, the rest of the PR-loop time (reading, replying, resolving) and the deploy (outside its `[wait: …]` intervals) as **Development**; `[wait: …]` intervals (suite, build, CI, Trivy, reviewer) and each pre-commit review round (`Code review round N started` → `completed`) as **Testing**. All task time is booked; each minute gets exactly one type — a wait or review interval inside, e.g., the implementation span is booked as Testing, and the rest of that span as Development (the task total stays the same, nothing is booked twice).

**Step 8: PR Review Loop (mandatory when a PR exists)**

Reviewer-agnostic: it applies to any reviewer on the PR — a human or a bot (currently Greptile, a GitHub App) — and to both forms a review can take.

- **Inline review threads.** Discover the PR number via `gh pr view --json number -q .number` if not already known. Fetch the threads with their resolution state via GraphQL (`gh pr view --json` has no `reviewThreads` field, and the REST comments endpoint has no `isResolved`):
  `gh api graphql --paginate -f query='query($o:String!,$r:String!,$n:Int!,$endCursor:String){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100,after:$endCursor){pageInfo{hasNextPage endCursor} nodes{id isResolved comments(first:100){nodes{databaseId author{login} createdAt body}}}}}}}' -F o=<owner> -F r=<repo> -F n=<pr>` — read **every** comment of a thread, not only the first (a reviewer may add a finding in a reply). Act on every node with `isResolved: false`, and on every resolved node with a comment newer than your own resolving reply (a reviewer answered after you resolved it — compare with your reply, not by author: the agent posts through the PO's GitHub account).
- **TRAP — late reviews:** a reviewer may post a new review *after* your last fetch. Each iteration, also fetch `gh api --paginate "repos/{owner}/{repo}/pulls/{pull_number}/reviews?per_page=100"` and re-read **every** review's body (bodies can be edited in place, so `submitted_at` is not enough), plus the inline comments of each new review (`repos/{owner}/{repo}/pulls/{pull_number}/reviews/{review_id}/comments`) — a review can carry its findings in the body without any inline thread.
- **Summary comment.** A reviewer may also post only a PR conversation comment (`gh api --paginate "repos/{owner}/{repo}/issues/{pull_number}/comments?per_page=100"`). On #279 Greptile posted such a summary (confidence score, risk note, "Last reviewed commit"). Wait until the summary references the **last pushed commit**; treat every concrete concern in it like a thread and answer it with a PR comment (`gh pr comment`).
- For each unresolved thread or concern, assess relevance: fix it if it identifies a genuine defect or in-scope improvement; explicitly explain and skip it if it is stale or out of scope. In all cases post a reply (`gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies -f body="..."` for threads), then resolve the thread — a reply alone never resolves it: `gh api graphql -f query='mutation($t:ID!){resolveReviewThread(input:{threadId:$t}){thread{isResolved}}}' -F t=<thread id>` (the node `id` from the query above).
- After applying fixes, re-run the full test suite (`docs/protocols/verification.md`) and — if a walkthrough or specification changed — the planning audit (`validate-planning.py --fail-on all`) before proposing a follow-up commit. A `/code-review high` round on the whole task diff follows the further-round rule of Step 7, *Pre-commit Review* (the agent proposes, the PO confirms).
- Repeat — fetch → assess → fix/reply → test → commit — until the **exit condition** holds: **green CI on the last pushed commit — always required**, and no unresolved threads, and — for a reviewer that posts a summary — that summary references the last pushed commit (the no-response rule below can replace only this reviewer part, never green CI). The PO merges.
- **No response:** if no reviewer has responded ~15 min after the push (`[wait: reviewer]`), do not block — record "no review received" and continue. A bot message that is not a review (e.g. Greptile's "Your trial has ended" on #278), or a summary that still does not reference the last pushed commit ~15 min after the push, counts as no response. A review that **arrives later is still handled**: before the merge it re-opens this loop; after the merge its findings become a follow-up (fix commit or backlog entry). Before reporting the task done — and whenever the PO asks — re-check the PR for new reviews; if the loop re-opens after the YouTrack record (2.15), set the State back to `In Progress`, and when it exits again add the new work items and a comment summarising the extra round.
