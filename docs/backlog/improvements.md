# Improvement Backlog

This document serves as a backlog for non-critical improvements, ideas, and minor issues that are discovered during development.

Items listed here are candidates for inclusion in future development cycles. Each item should be reviewed and prioritized during the planning phase of a new version.

### Frontend Performance

*   **Build-time pre-render of SystemMetadata static strings (POV-202 out-of-scope):** The changelog/roadmap modal renders markdown→HTML at runtime from *static* i18n strings (`system.changelog_entries`, `system.roadmap_phases`). These could be pre-rendered to HTML at build time, removing `react-markdown` from the `SystemMetadata` chunk. **Deferred because:** (1) it cannot remove `react-markdown` from the app — 5 dynamic AI/user-content consumers keep it (BriefingDetailPage, PublicBriefingView, PublicSummaryView, admin SummaryModal); (2) POV-202 already lazy-loads `SystemMetadata`, so its markdown cost is off every initial load; (3) it introduces a build step + a `dangerouslySetInnerHTML` surface for a ~3.8 KB-gzip saving on an already-deferred cold path. Only worth it if the modal's cold-open latency becomes a measured problem.
*   **Initial-bundle-size budget check in CI (POV-202 follow-up):** Add a CI gate that fails the build if the landing-page initial-load JS exceeds a gzip threshold. Threshold anchor = the **POV-202 post-optimization baseline of ~167 KB gzip** (NFR **P-5** in `docs/sdlc/02_non_functional_requirements.md`); a sensible ceiling is ~250 KB with headroom. Implementation options: a `size-limit`/`bundlesize` step against `vite build` output, or a small script parsing the build's reported gzip sizes. This is the enforcement half of the aspirational P-5 NFR; deferred as a genuine fast-follow because the threshold could only be set *from* POV-202's output.
*   **Lighthouse CI performance budget (POV-202 follow-up):** Add Lighthouse-CI (or an equivalent headless-Chrome audit) against a `vite preview` production build for the landing page, failing/warning below a performance-score floor. Anchor = POV-202 baseline **score 93** (NFR **P-5**); a floor of **≥90** is reasonable. Pairs with the bundle-size budget above to guard both transfer size and rendered performance. The repo already has `.agent/skills/performance-profiling/scripts/lighthouse_audit.py` as a manual starting point (note: it currently requires a globally-installed `lighthouse` CLI; CI would use `npx lighthouse` or `treosh/lighthouse-ci-action`).
*   **Frontend lint debt cleanup (POV-202 finding):** `npm run lint` reports **31 pre-existing errors** across ~17 files on the clean branch (independent of POV-202): nested ternaries (`sonarjs/no-nested-conditional`), unused vars (`@typescript-eslint/no-unused-vars`), misused promises in JSX handlers (`@typescript-eslint/no-misused-promises`), unnecessary type assertions, etc. The lint baseline is already red, which weakens the "lint clean" Definition-of-Done gate. Schedule a dedicated cleanup task (or `eslint --fix` sweep + manual review for the non-auto-fixable ~27) to restore a green lint baseline so future tasks can enforce it.

### Backend & Architecture

*   **Auth on the management interface / Prometheus scrape (POV-207 follow-up):** Since POV-207 the technical endpoints (`/q/metrics`, `/q/health`, `/q/openapi`) live on the management interface (port 9000), protected only by the Docker-network boundary (`quarkus.management.auth.enabled` is `false`). Sufficient while Prometheus runs in the same Docker network. Add management-interface auth (`quarkus.management.auth.*`, e.g. basic auth + Prometheus `basic_auth`) if Prometheus ever moves outside the network, or as defense in depth against network-internal bridges (Grafana admin can target `app:9000`; see RUNBOOK §13.2).
*   **`OpenApiGeneratorTest` writes the wrong artifact (POV-207 finding):** the test fetches the *served* OpenAPI document (YAML by default) and writes it into `backend/target/openapi.json`, overwriting the build-time JSON from `quarkus.smallrye-openapi.store-schema-directory`. The served test-profile document also contains 6 test-only paths (`/api/admin`, `/api/public`, `/api/secured`, `/api/v1/test-idempotency*`), which orval (`npm run gen:api`) then reads. **Evidence that it already leaks:** the committed client contains `frontend/src/api/generated/test-resource/test-resource.ts`, `dummy-idempotent-resource/dummy-idempotent-resource.ts` and three `model/postApiV1TestIdempotency*Body.ts` — generated from test-only resources. Either drop the test (the build already emits the schema) or have it request `?format=json` and write to a separate file; exclude test resources from the schema used for client generation, then delete the leaked generated files. Natural fit: POV-206, which regenerates the client anyway (orval upgrade).
*   **Dev Prometheus scrapes a non-existent target (POV-207 finding):** `backend/docker-compose.yml` (dev) mounts the same `prometheus.yml` as prod, whose target `app:9000` exists only in the prod network — dev has no `app` service (Quarkus runs on the host). Dev scraping never worked. Give dev its own scrape config targeting `host.docker.internal:8080` (the `extra_hosts` entry is already there) — in dev the management interface is disabled (`%dev.quarkus.management.enabled=false`), so metrics are on 8080. Caveat: in dev/test Quarkus binds to `localhost` by default (both HTTP and management host), so a container reaching the host gateway gets *connection refused* unless dev also sets `%dev.quarkus.http.host=0.0.0.0` (note: exposes dev on the LAN — prefer a loopback-only alternative if one exists).
*   **RUNBOOK still describes an OCI production host (POV-207 finding):** production runs on the local Docker stack (RUNBOOK §10, `.env.docker`, Cloudflare tunnel), but §16.1b and the transcript-proxy sections still refer to "the OCI backend host". Reconcile the RUNBOOK with the actual deployment topology.
*   **Longer browser session / own cookie name (POV-208 finding):** `application.properties` long claimed a 12 h session and a `POVZETKAR_SESSION` cookie; neither was ever in effect (dead `quarkus.http.auth.session.*` keys, removed in POV-208). The real session is `q_session`, living for the Google ID token (≈1 h) + `session-age-extension` (5 min), then a (usually silent) Google re-authentication. If a longer session is wanted: enable `quarkus.oidc.token.refresh-expired=true` with `offline_access`-style refresh tokens and a matching `session-age-extension`, or `quarkus.oidc.authentication.cookie-suffix` for a distinct name — user-visible (renaming logs everyone out once), so it needs its own task and PO decision.
*   **Validate custom config namespaces (POV-208 follow-up):** `QuarkusConfigKeysTest` checks only `quarkus.*` keys against the extensions' config models. Custom keys (`povzetkar.*`, `transcript.*`, `gemini.*`, `youtube.*`, `google.*`) have no such source of truth; a typo there is also silent. Option: move groups to `@ConfigMapping` interfaces with `smallrye.config.mapping.validate-unknown=true` for their prefixes, or a test comparing keys against the `@ConfigProperty`/`@ConfigMapping` declarations in the code.
*   **Validate `QUARKUS_*` environment variables too (POV-208 review):** `QuarkusConfigKeysTest` checks only the two `application.properties` files. Quarkus config set via environment (`docker-compose*.yml`, Dockerfile `ENV`, `.env*`) is the same defect class — POV-208 removed `QUARKUS_SWAGGER_UI_ALWAYS_INCLUDE` from `docker-compose.prod.yml`, a build-time property that a runtime environment variable cannot change. The config models already carry each property's exact `environmentVariable` name and `phase`, so the guard could parse `QUARKUS_*` entries from compose/Dockerfile and reject unknown names and `BUILD_TIME` properties set at runtime. `.env.docker` is not in git and stays out of reach.
*   **Unauthenticated XHR gets the 302 to Google in production, not 401 (POV-208 finding, verified 2026-09-25):** `CorsPreflightHandler.handleAjaxRedirect` rewrites the OIDC 302 to 401 only for requests whose `Origin` is in `povzetkar.cors.allowed-origins` (`FRONTEND_URL`). Production's `FRONTEND_URL` lists only `http://localhost:5173` / `http://127.0.0.1:5173`, and browsers omit `Origin` on same-origin GET anyway — so in production an expired-session XHR (`X-Requested-With: XMLHttpRequest`) receives `302 → accounts.google.com` with or without `Origin` (curl, after the POV-208 deploy); the SPA's 401 interceptor never fires and the fetch fails on the cross-origin redirect. Pre-existing (POV-208 changed no effective setting). The Vite dev proxy has its own rewrite, which masks this in dev. Fix: apply the XHR 302→401 rewrite to every `X-Requested-With: XMLHttpRequest` request independent of CORS (or set `quarkus.oidc.authentication.java-script-auto-redirect=false` and handle Quarkus' 499 in `client.ts`); then drop the Vite rewrite if redundant. Also decide whether production `FRONTEND_URL` should list the public origin.
*   **`*IT.java` integration tests never run (POV-208 finding):** no `maven-failsafe-plugin` is configured in the root or backend POM, so `./mvnw verify` (and CI) runs only surefire — `ApplicationHealthIT` and any other `*IT` class is silently skipped, although CLAUDE.md and the testing guide say they run under `verify`. Add failsafe (`integration-test` + `verify` goals, Quarkus `@QuarkusIntegrationTest` needs the packaged app) or correct the docs.
*   **Restrict forwarded-header trust to Caddy (POV-208 review, hardening):** `quarkus.http.proxy.proxy-address-forwarding` + `enable-forwarded-host` are on without `quarkus.http.proxy.trusted-proxies`, so `X-Forwarded-Host/Proto/For` are honored from any peer that reaches `app:8080`. Only Docker-network containers can (Caddy, cloudflared, Grafana, Prometheus), so this is defense in depth, not an open hole: a compromised container could skew OIDC redirect-URI construction, the Secure-cookie decision and client IPs in audit logs. Set `trusted-proxies` to the Caddy container address/network once it is stable (fixed IP or subnet in compose).

*   **OrchestrationManager → OrchestrationService rename:** Evaluated during v0.17.0 planning (2026-05-20) and **rejected**. The class is a true coordinator over six leaf services (`OrchestrationLockService`, `TopicProcessor`, `BriefingService`, `JustInTimeSummarizationScheduler`, `EventBroadcaster`, `MeterRegistry`); the "Manager" suffix carries useful semantic distinction from leaf `*Service` siblings. If reconsidered later, `OrchestrationCoordinator` would be a more accurate target than `OrchestrationService`. Note: historical docs reference the current name — rename would falsify those records.
*   **`update-version.cjs` sandbox compatibility:** Script invokes `mvnw.cmd` without `.\` prefix. Works in interactive shells but fails in restricted environments where `NoDefaultCurrentDirectoryInExePath=1` is set (e.g., Claude Code sandbox). Hardening fix: prefix the invocation with `.\` (Windows) or run via `path.join(rootDir, mvnw)`. Low priority — only affects automated/sandboxed runs.

*   **GenAI RPD enforcement (not just metering):** POV-195 made `usageCount` accurately reflect Google's daily request limit (RPD) but added no *enforcement* — there is no pre-call gate that stops GenAI requests once a daily cap is reached (unlike transcript providers, which have `TranscriptProviderQuotaService`). *   **Transcript proxy crash-restart supervision + log rotation (POV-196):** On the Synology DS220j the proxy is launched once at boot by a DSM Task Scheduler task running `transcript-proxy/run-proxy.sh` (B1 — no restart loop). If `uvicorn` dies mid-run it stays down until reboot; recovery is currently manual (flip `TRANSCRIPT_PROXY_URL` to the Railway fallback). If this proves flaky in practice, add a restart loop to `run-proxy.sh` (`while true; do uvicorn ...; sleep 5; done`, with backoff to avoid a tight crash loop), or a lightweight watchdog scheduled task. **Also:** `run-proxy.sh` appends all output to `proxy.log` with no rotation — on a 512 MB DS220j this grows unbounded (every request is logged, with tracebacks on upstream failures). Add log rotation (DSM `logrotate`, or a Python `RotatingFileHandler` with uvicorn logging into it). Raised in Gemini review of PR #265. Deferred deliberately to prove stability first.

*   **Bind dev/test Postgres to loopback + move off the prod port (POV-205 finding):** In `backend/docker-compose.yml` the `postgres-dev` and `postgres-test` port mappings are `"5432:5432"` and `"5433:5432"`. Two problems: (1) without a host-IP prefix Docker binds them to `0.0.0.0`, exposing the databases on every network interface (LAN, and any direct-internet interface) — the prod compose already does this correctly with `"127.0.0.1:5432:5432"`; (2) `postgres-dev` collides with the prod container on host port 5432, so dev mode cannot run alongside the local prod stack (observed during POV-205: `postgres-dev` would not start, and the manual dev curl sweep was skipped). Fix both at once by giving dev/test their own loopback-bound host ports, e.g. `"127.0.0.1:5442:5432"` (dev) and `"127.0.0.1:5443:5432"` (test); update the corresponding `%test` JDBC URL / `DB_PORT` for dev accordingly. Note: **do not** move the *prod* database off 5432 for security reasons — it already listens on `127.0.0.1` only (verified via `netstat`: `127.0.0.1:5432 LISTENING`), so a different port would be pure security-through-obscurity (anyone with loopback access enumerates it instantly). Port choice is an operational-convenience concern, not a security one. The most hardened option for prod access is to drop the host binding entirely and use `docker exec povzetkar-db-prod psql ...`, since the app connects over the Docker network (`postgres-prod:5432`) and never needs the host port. Low urgency; free defense-in-depth plus removes the dev/prod port-collision footgun. Pre-existing; observed while running the test DB during POV-205.
