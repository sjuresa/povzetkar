# Improvement Backlog

This document serves as a backlog for non-critical improvements, ideas, and minor issues that are discovered during development.

Items listed here are candidates for inclusion in future development cycles. Each item should be reviewed and prioritized during the planning phase of a new version.

---

## Candidate Improvements

### UI/UX

*   **Expired session on the SSE stream still gets the 302 (POV-221 review finding, pre-existing):** `EventSource` (`useJobEvents.ts`, `/api/v1/events/stream`) cannot send `X-Requested-With`, so `XhrAuthenticationChallenge` does not recognise it and an expired session answers the stream with the 302 to Google — the browser reports a connection error and keeps reconnecting; the SPA never sees a 401 on that channel (its XHRs do, and re-authenticate). Option: also treat `Accept: text/event-stream` as a JavaScript request (401), and let `useJobEvents` close the stream and defer to the XHR 401 flow on repeated errors.
*   **Friendly SPA 404 page (POV-221 follow-up):** since POV-221 a path outside the frontend routes gets a bare 404 from `SpaRoutingHandler` (empty body). A mistyped or outdated link inside the app therefore shows the browser's blank error page. Option: answer browser navigations (`Accept: text/html`) with the SPA shell and status 404, plus a router `notFoundComponent` (i18n) — keep the bare 404 for everything else, so probes stay cheap and visible.
*   **Admin Jobs Cancel Action:** Add cancel button to the Background Job Dashboard (`/admin/jobs`). Frontend implementation is straightforward once the backend signal mechanism is in place — see "Background Job Cancel (Signal Mechanism)" in the Backend section. Deferred from POV-188 (v0.17.0); restart + audit trail already delivered.
*   **"What's new" for visitors (POV-220 PO feedback):** the changelog/roadmap modal (`SystemMetadata`) shows `system.changelog_entries` / `system.roadmap_phases`, generated by `sync_metadata.py` from `CHANGELOG.md` and `roadmap.md` — engineering prose (task IDs, Quarkus, Trivy). POV-220 removed it from the landing page; inside the app it stays. If visitors should see product news, add a curated, marketing-level release note per version (e.g. a `### Highlights` block the release checklist fills and `sync_metadata.py` reads) instead of the raw summaries.
*   **Missing i18n keys (POV-220 finding, pre-existing):** `common.summary` (`SummaryModal.tsx:102`) and `briefingDetail.unknownAuthor` (`BriefingDetailPage.tsx:259`, `PublicBriefingView.tsx`, `PublicSummaryView.tsx`) exist in neither locale, so the raw key is shown. Add both keys (SL per `docs/guides/i18n-glossary.md`) and consider a test that every static `t('…')` key in `src/` exists in `en.json`.
*   **Advanced Audit Log Filtering:** (POV-142 Success-Enhancement) Extend the Audit Log UI with date-range pickers and a "Request Metadata" search capability to improve troubleshooting speed.
*   **Profile Image Upload:** (POV-146 Extension) Implement a profile image upload/management feature for the `/me` page, integrating with the backend user storage.
*   **Anonymous Demo Trial (no OIDC):** Allow visitors to click "Preizkusi demo" on the landing page and view demo content without Google sign-in. v0.17.0 already covers the equivalent experience via OIDC sign-in (new users land in `PENDING_APPROVAL` with `demo` role and see demo content via impersonation), so this is only justified if there's a real friction signal from users who refuse to sign in with Google. Two viable implementations when needed: (B1) dedicated `@PermitAll` public endpoints under `/api/v1/public/demo/*`, or (B2) synthetic session issued for the demo user without OIDC. Decide at implementation time.
*   **Background Job Cancel (Signal Mechanism):** Implement cancel for `RUNNING` background jobs. Requires: (1) `cancelRequested` boolean flag on `BackgroundJob` entity + migration, (2) check-points in `OrchestrationManager` — between pages in `processPendingAndRetryItemsByPage` and between topics in `executeTopicProcessingForDate`, (3) `POST /api/v1/admin/jobs/{id}/cancel` endpoint with guard that prevents overwrite of CANCELLED status by the lifecycle's final `updateJobStatus` call. Without the signal mechanism, any status update is meaningless — `executeJobLifecycle` will overwrite it with `COMPLETED` when the chain finishes. Deferred from POV-188 (v0.17.0). Estimated ~4-6h backend. (See also UI/UX entry above.)
*   **Markdown Rendering Inconsistency (DRY):** The plugin stack is already shared as `REHYPE_PLUGINS` (`frontend/src/utils/markdown`) and used by the 5 call-sites in `BriefingDetailPage`, `PublicBriefingView` and `PublicSummaryView`. Three call-sites still pass no plugins: `SummaryModal.tsx` (admin, AI summary text) and `SystemMetadata.tsx` (changelog + roadmap). Not a security gap — without `rehypeRaw` react-markdown does not render raw HTML — but external links there do not open in a new tab and the rendering differs. Fix: a shared `<MarkdownContent>` wrapper with `REHYPE_PLUGINS`, used by all 8 call-sites.
*   **E2E Visual Regression Testing (POV-178 Follow-up):** Integrate visual snapshot testing (Playwright `toHaveScreenshot`) for critical UI states (Trigger Modal, Briefing Viewer) to catch design regressions that don't trigger functional failures.

### Frontend Performance

*   **Build-time pre-render of SystemMetadata static strings (POV-202 out-of-scope):** The changelog/roadmap modal renders markdown→HTML at runtime from *static* i18n strings (`system.changelog_entries`, `system.roadmap_phases`). These could be pre-rendered to HTML at build time, removing `react-markdown` from the `SystemMetadata` chunk. **Deferred because:** (1) it cannot remove `react-markdown` from the app — 5 dynamic AI/user-content consumers keep it (BriefingDetailPage, PublicBriefingView, PublicSummaryView, admin SummaryModal); (2) POV-202 already lazy-loads `SystemMetadata`, so its markdown cost is off every initial load; (3) it introduces a build step + a `dangerouslySetInnerHTML` surface for a ~3.8 KB-gzip saving on an already-deferred cold path. Only worth it if the modal's cold-open latency becomes a measured problem.
*   **Initial-bundle-size budget check in CI (POV-202 follow-up):** Add a CI gate that fails the build if the landing-page initial-load JS exceeds a gzip threshold. Threshold anchor = the **POV-202 post-optimization baseline of ~167 KB gzip** (NFR **P-5** in `docs/sdlc/02_non_functional_requirements.md`); a sensible ceiling is ~250 KB with headroom. Implementation options: a `size-limit`/`bundlesize` step against `vite build` output, or a small script parsing the build's reported gzip sizes. This is the enforcement half of the aspirational P-5 NFR; deferred as a genuine fast-follow because the threshold could only be set *from* POV-202's output.
*   **Lighthouse CI performance budget (POV-202 follow-up):** Add Lighthouse-CI (or an equivalent headless-Chrome audit) against a `vite preview` production build for the landing page, failing/warning below a performance-score floor. Anchor = POV-202 baseline **score 93** (NFR **P-5**); a floor of **≥90** is reasonable. Pairs with the bundle-size budget above to guard both transfer size and rendered performance. The repo already has `.agent/skills/performance-profiling/scripts/lighthouse_audit.py` as a manual starting point (note: it currently requires a globally-installed `lighthouse` CLI; CI would use `npx lighthouse` or `treosh/lighthouse-ci-action`).
*   **Frontend lint debt cleanup (POV-202 finding):** `npm run lint` reports **27 errors + 2 warnings** on the clean branch (2026-10-01; 31 at POV-202, 5 auto-fixable): nested ternaries (`sonarjs/no-nested-conditional`), unused vars (`@typescript-eslint/no-unused-vars`), misused promises in JSX handlers (`@typescript-eslint/no-misused-promises`), unnecessary type assertions, etc. The lint baseline is already red, which weakens the "lint clean" Definition-of-Done gate. Schedule a dedicated cleanup task (or `eslint --fix` sweep + manual review for the rest) to restore a green lint baseline so future tasks can enforce it.

### Backend & Architecture

*   **Auth on the management interface / Prometheus scrape (POV-207 follow-up):** Since POV-207 the technical endpoints (`/q/metrics`, `/q/health`, `/q/openapi`) live on the management interface (port 9000), protected only by the Docker-network boundary (`quarkus.management.auth.enabled` is `false`). Sufficient while Prometheus runs in the same Docker network. Add management-interface auth (`quarkus.management.auth.*`, e.g. basic auth + Prometheus `basic_auth`) if Prometheus ever moves outside the network, or as defense in depth against network-internal bridges (Grafana admin can target `app:9000`; see RUNBOOK §13.2).
*   **Dev Prometheus scrapes a non-existent target (POV-207 finding, confirmed in POV-214):** `backend/docker-compose.yml` (dev) mounts the prod `backend/infra/monitoring/prometheus/prometheus.yml`, whose only target `app:9000` exists only in the prod network — dev has no `app` service (Quarkus runs on the host via `quarkus dev`). Dev Prometheus/Grafana never showed data. Options: a dev-only `prometheus.dev.yml` targeting `host.docker.internal:8080`, metrics path `/q/metrics` (the `extra_hosts` entry is already there; in dev the management interface is off, `%dev.quarkus.management.enabled=false`), or drop Prometheus/Grafana from the dev stack if nobody uses them. Caveat: in dev Quarkus binds to `localhost`, so a container reaching the host gateway gets *connection refused* unless dev also sets `%dev.quarkus.http.host=0.0.0.0` (exposes dev on the LAN — prefer a loopback-only alternative if one exists).
*   **Longer browser session / own cookie name (POV-208 finding):** `application.properties` long claimed a 12 h session and a `POVZETKAR_SESSION` cookie; neither was ever in effect (dead `quarkus.http.auth.session.*` keys, removed in POV-208). The real session is `q_session`, living for the Google ID token (≈1 h) + `session-age-extension` (5 min), then a (usually silent) Google re-authentication. If a longer session is wanted: enable `quarkus.oidc.token.refresh-expired=true` with `offline_access`-style refresh tokens and a matching `session-age-extension`, or `quarkus.oidc.authentication.cookie-suffix` for a distinct name — user-visible (renaming logs everyone out once), so it needs its own task and PO decision.
*   **Validate custom config namespaces (POV-208 follow-up):** `QuarkusConfigKeysTest` checks only `quarkus.*` keys against the extensions' config models. Custom keys (`povzetkar.*`, `transcript.*`, `gemini.*`, `youtube.*`, `google.*`) have no such source of truth; a typo there is also silent. Option: move groups to `@ConfigMapping` interfaces with `smallrye.config.mapping.validate-unknown=true` for their prefixes, or a test comparing keys against the `@ConfigProperty`/`@ConfigMapping` declarations in the code.
*   **Validate `QUARKUS_*` environment variables too (POV-208 review):** `QuarkusConfigKeysTest` checks only the two `application.properties` files. Quarkus config set via environment (`docker-compose*.yml`, Dockerfile `ENV`, `.env*`) is the same defect class — POV-208 removed `QUARKUS_SWAGGER_UI_ALWAYS_INCLUDE` from `docker-compose.prod.yml`, a build-time property that a runtime environment variable cannot change. The config models already carry each property's exact `environmentVariable` name and `phase`, so the guard could parse `QUARKUS_*` entries from compose/Dockerfile and reject unknown names and `BUILD_TIME` properties set at runtime. `.env.docker` is not in git and stays out of reach.
*   **`*IT.java` integration tests never run (POV-208 finding):** no `maven-failsafe-plugin` is configured in the root or backend POM, so `./mvnw verify` (and CI) runs only surefire — `ApplicationHealthIT` and any other `*IT` class is silently skipped, although CLAUDE.md and the testing guide say they run under `verify`. Add failsafe (`integration-test` + `verify` goals, Quarkus `@QuarkusIntegrationTest` needs the packaged app) or correct the docs.

*   **OrchestrationManager → OrchestrationService rename:** Evaluated during v0.17.0 planning (2026-05-20) and **rejected**. The class is a true coordinator over six leaf services (`OrchestrationLockService`, `TopicProcessor`, `BriefingService`, `JustInTimeSummarizationScheduler`, `EventBroadcaster`, `MeterRegistry`); the "Manager" suffix carries useful semantic distinction from leaf `*Service` siblings. If reconsidered later, `OrchestrationCoordinator` would be a more accurate target than `OrchestrationService`. Note: historical docs reference the current name — rename would falsify those records.
*   **`Clock` injection in `TranscriptProviderQuotaService`:** Inject `java.time.Clock` instead of calling `YearMonth.now(ZoneOffset.UTC)` directly to allow deterministic testing of period-based quota logic. Raised in Gemini review of PR #252.
*   **GenAI RPD enforcement (not just metering):** POV-195 made `usageCount` accurately reflect Google's daily request limit (RPD) but added no *enforcement* — there is no pre-call gate that stops GenAI requests once a daily cap is reached (unlike transcript providers, which have `TranscriptProviderQuotaService`). If RPD exhaustion becomes a real problem, add a pre-call check against `getUsageForToday()` with a configured cap plus a fallback/queue strategy. New mechanism, not a tweak to the counter.
*   **Transcript retry state in the admin UI (POV-222 follow-up):** `transcript_attempts` / `next_transcript_attempt_at` (V38) are not shown anywhere; an admin sees `RETRY_LATER` without knowing when the next automatic attempt is due or how many are left, and can give a video a fresh budget only in the database. Option: show "attempt n of 7, next at …" in the admin item list and offer a "reset retries" action (audited).
*   **Transcript proxy crash-restart supervision + log rotation (POV-196):** On a self-hosted proxy host the proxy is launched once at boot by a scheduled boot task running `transcript-proxy/run-proxy.sh` (B1 — no restart loop). If `uvicorn` dies mid-run it stays down until reboot; recovery is manual (restart the proxy; there is no second proxy host since POV-223). If this proves flaky in practice, add a restart loop to `run-proxy.sh` (`while true; do uvicorn ...; sleep 5; done`, with backoff to avoid a tight crash loop), or a lightweight watchdog scheduled task. **Also:** `run-proxy.sh` appends all output to `proxy.log` with no rotation — on a small host this grows unbounded (every request is logged, with tracebacks on upstream failures). Add log rotation (`logrotate`, or a Python `RotatingFileHandler` with uvicorn logging into it). Raised in Gemini review of PR #265. Deferred deliberately to prove stability first.
*   **Inline HQL in services and resources (POV-216 finding) — → POV-218:** QA rule 3 (rev. POV-216) requires queries to live in named entity/repository methods that a DB-backed persistence test calls — new or changed queries only. Eight existing classes still inline HQL strings (`UserContextService`, `ContentItemApiResource`, `SourceItemApiResource`, `TopicApiResource`, `UserApiResource`, `ui/AdminResource`, `ui/SummaryResource`, `ui/TopicResource`), so under `PanacheMock` their query text is never executed by a test. Move them into named entity methods with persistence tests when those classes are next touched, or as one refactoring task (Green-to-Green).
*   **SSE events are broadcast to all users — scope them per user (POV-216 finding) — → POV-217:** `EventBroadcaster` sends every event on `/api/v1/events/stream` to every connected `ROLE_USER` identity (all approved users and admins) with no owner filter: `JOB_STATUS_CHANGED` (with `details`) and `ORCHESTRATION_COMPLETED` / `ORCHESTRATION_PREVIEW_COMPLETED` (preview message with item counts) raise toasts and sounds for other users' jobs — cross-account UX noise and a minor information leak, low urgency while all accounts are admin-vetted. Fix: carry the owning `userId` in events and filter `getEventStream()` per connected user (system-wide events for admins only). Would also allow an `ACCOUNT_STATUS_CHANGED` push to replace the pending-status polling added by POV-216.
*   **Scheduler integration test with real lock/DB service (POV-197 follow-up) — done in POV-213 (v0.20.0):** `ScheduledOrchestrationIntegrationTest` lets the real scheduler fire the job (TC-ING-006, `docs/guides/testing.md` §2.6). Original entry: The `@Scheduled` orchestration bug (`BlockingOperationNotAllowedException` on every invocation) was invisible to the test suite because the scheduler tests `@InjectMock OrchestrationLockService`, so the blocking DB call that triggers the IO-thread violation never ran. Add an integration-test variant that exercises the `@Scheduled` entry point against the *real* lock service + test DB to catch this class of bug (synchronous blocking before the first `Uni` boundary on an IO thread). This is the standing blind spot called out in the v0.18.0 cross-task retrospective — three tasks this version hit bugs that mocks hid.
*   **Overlapping orchestration runs race on the briefing and the lock (POV-213 review finding, pre-existing):** the orchestration lock is per date, so two overlapping runs (scheduled + manual, or two manual) split the dates between them, and both generate the same day's briefing. `generateBriefingForTopicUni` checks and then inserts (`OrchestrationManager`), and `DefaultBriefingGenerator.generateBriefing`'s `PESSIMISTIC_WRITE` lock covers no row while the briefing does not exist yet — a concurrent insert violates `uc_topic_id_briefing_date` and the step counts as failed. Likewise `acquireLock` on a fresh date can hit a unique violation that is not an `OrchestrationLockException`. Option: insert-or-ignore (`ON CONFLICT DO NOTHING`) for both, or one run-level lock for scheduled and manual runs.
*   **Guard against `Uni`/`CompletionStage`-returning `@Scheduled` methods (POV-213 out-of-scope):** Quarkus runs a `@Scheduled` method that returns `Uni<Void>`/`CompletionStage<Void>` (or is `@NonBlocking`) on the event loop and ignores `@Blocking` on it — the POV-197 defect class. `ScheduledOrchestrationIntegrationTest` covers only the orchestration job; the other three jobs return `void` today. Option: an architecture test (reflection or ArchUnit-style scan) that fails on any `@Scheduled` method with a non-`void` return type or `@NonBlocking`, unless allow-listed with a reason.
*   **Remove `POVZETKAR_BRIEFING_CRON` from the deployment's environment file (POV-197 cleanup):** `povzetkar.briefing.cron` was removed from `application.properties` when the separate daily-briefing cron was folded into the unified periodic orchestration. Quarkus ignores a stale `POVZETKAR_BRIEFING_CRON` env var (no error), but it should be removed from the environment file where it was set to avoid operator confusion. Trivial ops cleanup.
